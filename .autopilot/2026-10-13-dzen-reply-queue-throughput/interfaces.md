# Общий контракт реализации

## Границы, решённые в спецификации

- Оркестратор `dzen_commenter/orchestrator/loop.py` владеет порядком обработки очередей и выбором короткого/полного сканирования. `run_cycle()` остаётся точкой запуска цикла; генерация ограничена пачкой и часовым лимитом.
- Repository `dzen_commenter/db/repository.py` владеет атомарным claim, lease, retry, SQL-порядком generation jobs и durable-журналом квоты AI-вызовов. Единственная новая миграция в этой задаче — аддитивная таблица журнала.
- Studio adapter `dzen_commenter/dzen/page.py` владеет прокруткой, раскрытием ответов и DOM snapshot; обе глубины сканирования возвращают существующие `Comment`.
- Существующие synthetic IDs, upsert, claim tokens, статусы и безопасная обработка неопределённой публикации сохраняются.

## Общие правила проекта

- Python 3.11; Playwright sync; SQLAlchemy/PostgreSQL; без новых зависимостей. Миграция разрешена только для аддитивного журнала AI-вызовов из Ticket 02.
- Полный набор: `python -m pytest -q`; один файл: `python -m pytest -q <path>`; стиль: `ruff check .`.
- Изменения только в зонах текущего ticket. Не редактировать `.env`, секреты, runtime config и production-данные.
- Не записывать в логи тексты комментариев, имена авторов, URL, токены или HTML.
- Проверки используют fake/injected-компоненты; не выполнять реальную авторизацию или публикацию в Дзене.
- Не расширять изменение схемы за пределы аддитивного журнала AI-вызовов из Ticket 02; любые другие новые миграции или зависимости вернуть как `BLOCKED`.

## Из таска 01 — порядок выбора generation jobs

- `claim_next_generation(now)` остаётся владельцем атомарного выбора и lease.
- Приоритет свежести: `posted_at`, затем `fetched_at`; retry, чей `next_attempt_at` ещё не наступил, не выдаётся.

## Фактически из таска 01

- Публичная сигнатура не изменилась: `claim_next_generation(now: datetime) -> ClaimedGeneration | None`.
- Query упорядочивает eligible jobs по времени комментария: `posted_at`, fallback на `fetched_at`, с детерминированным tie-break; due-time retry и claim-token остаются в атомарном repository path.

## Из таска 02 — цикл и bounded drain

- Обрабатывать готовую очередь до Studio-сканирования; максимум 5 generation jobs за цикл, а каждый фактический вызов модели — не выше durable-остатка часовой квоты.
- Не более одной безопасной публикации за цикл; ошибки сканирования не отменяют работу очереди, уже сделанную в этом цикле.
- Перед каждым фактическим вызовом модели, включая shortening retry, repository атомарно резервирует слот в durable-журнале AI-вызовов. Журнал не хранит пользовательский текст, авторов, URL или секреты; запись создаётся до сетевого вызова. Миграция переносит только timestamps legacy Reply-записей за скользящий час, не меняя исходные строки.
- Внутренние сигнатуры: `reserve_ai_call(now: datetime, *, limit: int) -> bool` и `release_generation_claim(comment_id: int, *, claim_token: str) -> None`. `false` от reservation означает, что квота исчерпана, provider не вызывается, а только совпадающий активный claim возвращается в очередь без увеличения attempt count; stale token ничего не меняет.

## Из таска 03 — режимы Studio

- Частое чтение ограничено первыми 100 карточками; периодическое полное чтение продолжает находить поздние комментарии в старых публикациях.
- Полный проход сохраняет существующее раскрытие ответов, fail-closed snapshot и идемпотентное сохранение.
- Production-адаптер предоставляет `fetch_recent_comments(*, max_cards)` для ограниченного scan и сохраняет `fetch_comments()` как полный протокол сканирования. Оркестратор вызывает ограниченный метод с лимитом 100; для адаптера без него используется существующий полный путь.
- Время последнего успешного полного прохода хранится в процессе и обновляется только после успешного сканирования и сохранения; ошибка оставляет full scan due на следующем цикле.
