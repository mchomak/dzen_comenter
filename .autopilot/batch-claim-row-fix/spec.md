# Спецификация: исправление чтения batch-очереди и безопасное развёртывание

## Задача

Пакетная генерация не должна падать после появления строк в очереди: бот должен корректно получить время ожидания первой строки, сформировать batch и продолжить цикл.

## Решение

Исправить репозиторий PostgreSQL так, чтобы данные результата `select(CommentBatchQueueTable, CommentTable)` читались по документированным mapping-ключам, а не как ORM-экземпляр. Закрыть это интеграционным тестом repository. После code review отправить единственный новый commit в origin и развернуть его поверх существующей базы. Выполнить Compose restart/build всего набора без `down`/volume операций, дождаться окончания сборки и готовности app, admin и postgres, затем проверить свежие логи всех сервисов. В безопасном пилотном режиме batch включён, но автопубликация выключена. Каждая обнаруженная после выкладки новая ошибка создаёт новый локальный фикс, review, commit, push, deploy и повтор проверки; завершение допускается только без новых runtime ошибок.

## Решения по реализации

- `PostgresCommentRepository.claim_next_batch` владеет SQLAlchemy result shape и читает `queued_at` через явный `mappings()`/labelled columns либо другой эквивалентный контракт, согласованный с созданием `BatchItem`.
- Тест создаёт достаточно комментариев одного поста, ставит их в очередь и утверждает успешный claim; это прямое воспроизведение ветки, где раньше обращение к scalar `comment_id` как к `.queued_at` падало.
- Пакетный пилот остаётся с `batch_max_comments=3`, `batch_wait_hours=12`, cooldown `60`, двумя попытками и `auto_publish=false`. Это конфигурация безопасной проверки, а не изменение схемы.
- Перед финальным статусом orchestrator фиксирует успешное окончание Docker build и свежие логи app, admin и postgres. Любой новый error после выкладки возвращает работу к новому локальному исправлению и повторному deploy; неудачный цикл не считается завершением.
- Доступ к серверу выполняется только во время SSH-сеанса; секреты не сохраняются и не передаются агентам.
