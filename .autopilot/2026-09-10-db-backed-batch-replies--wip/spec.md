# Спецификация: DB-backed batch-ответы

## Цель

Ни один технически недоступный в текущем DOM-снимке комментарий не получает статус `skipped`. Планирование и генерация batch-ответа используют сохранённые данные PostgreSQL; DOM используется только для фактического ввода и публикации ответа.

## Решения

### Очередь генерации

`comments.status = new` остаётся бизнес-состоянием нового ожидающего комментария. `comment_batch_queue.state = queued` остаётся техническим состоянием ожидания: не вводится дублирующий `wait`.

Очередь группируется по `publication_id`/каноническому `post_url`. Claim выбирает полный batch размером `batch_max_comments`; если полный batch отсутствует, выбирается самая старая группа, у которой oldest `queued_at` достиг `batch_wait_hours`, даже если в ней один или два элемента. Claim и блокировки остаются транзакционными (`FOR UPDATE SKIP LOCKED`). Лимиты одного цикла и часовой AI-лимит сохраняются.

### Контекст статьи

Существующая `publications` — единственный владелец идентичности статьи, поэтому отдельная таблица с копией URL и заголовка не создаётся. В неё аддитивно добавляются nullable-поля: `article_text`, `article_fetched_at`, `article_content_hash`, `article_context_status`.

При генерации batch репозиторий возвращает сохранённый контекст статьи. Если текста ещё нет, цикл получает его через существующий `DzenPage.fetch_article_text(post_url)`, сохраняет результат и передаёт его в prompt. Ошибка получения статьи не блокирует batch: prompt получает пустой текст, как в текущем безопасном fallback; состояние контекста сохраняется для наблюдаемости. Существующие строки публикаций не переписываются миграцией.

### Результат генерации

Строгий parser и fallback для некорректного batch-ответа сохраняются. `REPLY` создаёт ответ в статусе `generated`; настоящий `ERROR` остаётся в generation-очереди с текущим лимитом повторов и cooldown. `SKIP` остаётся только осознанным результатом модели или бизнес-фильтра; он никогда не используется для технической недоступности комментария в DOM.

### Очередь публикации

Добавляется аддитивная `reply_publication_queue` с одним активным элементом на reply: `reply_id`, `state`, `attempt_count`, `next_attempt_at`, `last_error`, `created_at`, `claimed_at`.

После валидной генерации reply ставится в publication-очередь. Отдельная фаза цикла claim-ит готовые публикации с блокировкой, пытается `DzenPage.publish_reply`, и только при успехе ставит `published`/`generated` согласно `auto_publish`. Ошибка нахождения комментария в DOM или ошибка браузера возвращает publication-элемент в retry с отдельными live-настройками лимита и cooldown. Она не генерирует текст повторно, не меняет `comments.status` на `skipped` и не меняет generation-очередь.

После исчерпания publication-retry reply получает `error` с причиной, comment получает `error`, очередь завершается. Это наблюдаемая техническая неисправность, а не пропуск.

### Разрешение целевого комментария

Текущий Playwright-адаптер ищет комментарий по синтетическому ID в текущем снимке. Новая архитектура не обещает публикацию для комментария, который Дзен больше не выдаёт; она гарантирует сохранение ответа и корректный retry/diagnostics. Native ID или permalink комментария не добавляются без подтверждённого DOM-контракта Дзена; реальные запросы к Дзену для проверки не выполняются.

## Новые runtime-настройки

- `publication_retry_cooldown_minutes` — интервал повторной публикации.
- `publication_max_attempts_per_reply` — максимум попыток публикации.

Значения имеют безопасные defaults, валидируются как существующие batch-настройки и отображаются в админской форме. Это несекретные live-настройки.

## Миграция и безопасность

Уточнение пользователя от 2026-09-10: «да сделай, но также сделай перед этим новый бекам БД». Запрет «БД не удаляй и не меняй» относится к существующим данным production; разрешена только аддитивная миграция схемы.

Миграция добавляет nullable поля, новую таблицу и индексы. Она не удаляет, не обновляет и не переназначает существующие строки. Непосредственно перед `alembic upgrade head` на production создаётся timestamped `pg_dump -Fc` в `/root/backups`; проверка `pg_restore --list` обязательна. Deploy прекращается при неуспехе backup или миграции.

Порядок deploy: зелёные локальные тесты → отдельный commit → push в `origin/main` → сервер получает этот commit без принудительного изменения истории → production backup и его проверка → build/restart compose → `alembic upgrade head` из штатного entrypoint → проверка контейнеров, текущей ревизии Alembic и последних логов. При ошибке deploy останавливается; восстановление backup выполняется только по отдельному указанию пользователя.

## Приёмка

1. Неполная группа comments создаёт batch после `batch_wait_hours` и генерируется только из данных БД, даже если её комментариев нет в текущем snapshot.
2. Batch использует сохранённый текст статьи; при первом отсутствии cache текст статьи сохраняется после безопасной попытки fetch.
3. Корректный ответ сохраняется и ставится в publication-очередь; publication не вызывается внутри generation-транзакции.
4. `LookupError`/browser error при публикации не создаёт `SKIP`, не повторяет AI-вызов и создаёт publication retry с вычисленным cooldown.
5. Исчерпание publication retry завершает reply/comment как `error` с причиной, никогда как `skipped`.
6. Существующие тесты batch, repository, runtime config и admin проходят; добавлены изолированные fake-тесты всех новых путей, без реального браузера и Дзена.
7. Миграция проходит на пустой и текущей схеме; backup создан и проверен до production-миграции.

## Вне рамок

- Реальное исследование или изменение DOM Дзена.
- Автоматическое восстановление уже terminal `skipped` строк без сохранённой причины.
- Удаление либо изменение существующих данных production PostgreSQL.

## Границы и швы

| Модуль | Владеет | Выставляет |
|---|---|---|
| CommentRepository | транзакционным claim/save обеих очередей и article cache | методы claim/save context/publication outcome в существующем Protocol |
| OrchestratorLoop | порядком capture → generation → publication и квотами | один цикл с injected repository/page/provider |
| DzenPage | реальным DOM-вводом ответа | `publish_reply(comment, text, auto_publish)`; ошибки поиска — обычные исключения |
| RuntimeConfig | live несекретными лимитами | валидированные runtime settings |
