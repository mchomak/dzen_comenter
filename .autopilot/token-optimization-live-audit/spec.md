# Спецификация: Live-аудит дополнительных оптимизаций токенов

## Задача

Понять, какие части реального запроса бота и его жизненного цикла тратят токены без соразмерной пользы, и уменьшить доказанные потери так, чтобы качество ответа и рабочие границы сервиса не были угаданы вместо проверены.

## Решение

Будет воспроизводимый аудит production-данных без изменения production: выборки запросов и логов, точный подсчёт входных токенов текущим API модели, сравнение контролируемых вариантов контекста и проверка тестами. Для гипотез с измеримым эффектом появится минимальное изменение кода и тесты. Финальный отчёт отделит уже измеренное снижение от прогноза для изменения, которое ещё не развёрнуто.

## Решения по реализации

1. **Единица измерения — токены текущего endpoint модели, а не оценка по символам.** Это исключает неверный коэффициент для русского текста, URL и разметки.
2. **Production-аудит — только чтение.** SQL ограничивается `SELECT`; логи и runtime-настройки читаются без вывода секретных полей. Никакие новые данные на сервер не записываются.
3. **Сравнение — парное.** Для каждого сохранённого входа создаются текущий и кандидатный prompt с тем же комментарием/системными инструкциями; сравнивается число входных токенов. Выборка и правила исключения фиксируются в отчёте.
4. **Контекст является бюджетом, а не неограниченной строкой.** Если распределение подтвердит пользу, общий конструктор prompt получает детерминированный лимит для статьи и ветки: сохраняются метаданные и ближайший полезный текст, а отбрасываемое окончание явно отделяется. Для ветки выбран хвост 400 символов: на детерминированной production-выборке 100 исторических входов он сберёг 1 435 из 53 101 токена (2,70%) и затронул 12 входов; поток страницы добавляет предыдущие сообщения по времени, поэтому хвост сохраняет самые свежие.
5. **Выходные токены отделены от входных.** Лимит output изучается по фактическому распределению сохранённых ответов и не меняется без данных о качестве/обрезании.
6. **Повторы изучаются отдельно.** Превышение допустимой длины, сетевые повторы и ошибки считаются по БД/логам; это не смешивается с обычной ценой одного успешного prompt.
7. **Изменения кода минимальны.** Новая логика остаётся за существующими тестовыми швами prompt/loop/config; не меняет schema БД и не требует deploy для проверки.
8. **Развёртывание не входит в этот прогон.** Оно требует отдельного подтверждения пользователя и описывается только как следующий шаг.
9. **Денежная оценка не угадывается.** Если активный тариф невозможно доказать из официального источника или данных аккаунта, отчёт указывает точное снижение токенов и формулу стоимости, а не мнимую сумму.
10. **Генерационный тест ограничен и изолирован.** Он использует до трёх запросов с текущим ключом, публичным текстом статьи и одним нейтральным тестовым комментарием; не создаёт ответов в Дзене и не меняет БД.
11. **«Удалось снизить» имеет две шкалы.** Измеренная величина — разница токенов на сохранённых входах и контролируемых API-вызовах; production-величина появится только после отдельного развёртывания и не заявляется в этом read-only прогоне.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Контекст статьи | извлечение полезного текста публикации | `fetch_article_text(url) -> text` | DOM-селекторы и фильтрацию page chrome |
| Конструктор prompt | состав сообщения модели и бюджет контекста | `build_prompt(comment, article, thread, settings) -> text` | правила усечения и разметку частей prompt |
| Цикл ответов | вызов провайдера и ограничение генераций | обработку одного комментария | состояние дедупликации, публикации и retry |
| Провайдер AI | запросы к текущей модели | `generate(...)`, `count_tokens(...)` для аудита | авторизацию и transport |
| Аудит | read-only выборку и расчёт метрик | локальные отчёты и воспроизводимые агрегаты | соединение с сервером и секреты |

Швы для тестов: существующие Protocol/инъекции страницы и AI-провайдера, а также публичный конструктор prompt. Проверки не используют настоящий браузер, БД или production API.
