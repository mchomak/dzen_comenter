# Спецификация: своевременный конвейер ответов Дзена

## Задача

Бот накапливает комментарии и готовые ответы быстрее, чем успевает их публиковать. Длинный проход Studio задерживает обработку, а раздельные очереди могут оставить сохранённые ответы ждать публикации, пока генерируются новые. Нужен ограниченный рабочий список, в котором комментарий проходит генерацию, сохранение и публикацию последовательно, а старые задания закрываются с понятной причиной.

## Решение

Каждый цикл сначала обслуживает готовую очередь, и только после этого при наступившем сроке делает короткий Studio scan. Сначала бот публикует уже сохранённые ответы. Если готовых публикаций нет, он берёт доступный комментарий, получает контекст и ждёт модель не дольше заданного таймаута. Ошибка при получении/сохранении контекста, сохранении результата или при генерации ставит retry в конец очереди по `next_attempt_at`; пока действует cooldown, цикл берёт следующую готовую работу. После scan новые допущенные задания обрабатываются в том же цикле, если остался лимит попыток. Успешный ответ сразу сохраняется и пробуется к публикации. Ошибка публикации оставляет готовый ответ в БД и повторяет только публикацию, поставив попытку в конец очереди публикаций. Если submit мог пройти, но результат не подтверждён, ответ переводится в `unconfirmed` без повторного submit. Долговременная квота модели сохраняется между перезапусками.

Одновременно в активном окне не более 30 уникальных комментариев: generation, publication и все retry, включая отложенные. Один комментарий, который перешёл из generation в publication, занимает одно место, а не два. Избыток не удаляется: записи ожидают вне окна и заполняют свободные места, публикации имеют приоритет, generation выбирается по свежести. Устаревшие задания закрываются с явной причиной.

Studio проверяется только коротким способом: если Studio уже открыта, обновляется та же вкладка; считываются верхние 100 карточек и раскрываются доступные ответы. Проверка выполняется раз в 5 минут; при пустом активном окне — раньше, но не чаще раза в минуту. После старта проверка выполняется сразу. Полного прохода и fallback на него нет.

## Решения по реализации

- **Цикл:** общий bounded drain не больше `MAX_REPLIES_PER_CYCLE` work items за цикл. Сначала drain готовой очереди, затем наступивший короткий scan; новые допущенные jobs получают оставшийся бюджет того же цикла. В каждой итерации drain сначала публикация due сохранённого ответа; если её нет, взять одну generation; её первая немедленная publication attempt входит в тот же слот. Publication-only retry занимает один слот своего цикла. Ошибка одной generation не завершает drain, если квота и общий лимит цикла позволяют взять следующую ready задачу.
- **Квота и таймаут:** оставить durable AI reservation перед каждым фактическим вызовом, включая shortening; добавить единый настраиваемый HTTP timeout для обоих AI provider (`AI_REQUEST_TIMEOUT_SECONDS`), затем использовать существующий cooldown generation retry. Ограничение цикла не заменяет скользящую часовую квоту.
- **Сохранение результата:** Reply и его publication row фиксируются атомарно. Если commit временно не удался, повторить сохранение уже полученного текста; не считать generation завершённой, пока запись не подтверждена. Если процесс завершился до durable commit и результат утрачен, generation повторяется, так как сохранённого ответа для publication нет (A13).
- **Активное окно:** `MAX_ACTIVE_WORK_ITEMS=30` ограничивает число уникальных `comment_id`, для которых активна generation или publication работа; один комментарий, перешедший generation → publication, остаётся одним item. `queued`, действующие `claimed`, `submitting` и retry с будущим `next_attempt_at` считаются активными. Новые generation не допускаются, пока доступные места заняты публикациями. На коротком скане выбираются наиболее свежие eligible комментарии, пока общее число активных comment IDs не достигнет 30.
- **Работа вне окна:** применять `waiting` для незакрытых generation jobs, не удалять Comment/Reply и не сбрасывать `attempt_count`/`next_attempt_at`; jobs в `waiting` не claim-ятся. Только первая reconciliation может выбрать наиболее свежие eligible legacy generation jobs в свободные слоты; все остальные known jobs не реадмитятся. Все saved generated Reply получают publication queue row и имеют приоритет для свободных слотов. Когда saved публикаций больше 30, оставшиеся сохраняются и ждут слота перед публикацией. После startup свободные generation slots заполняются только ещё не известными card IDs текущего short scan по `coalesce(posted_at, first fetched_at)` по убыванию с id как стабильным tie-break (A14).
- **Просрочка:** использовать `coalesce(posted_at, first fetched_at)` и действующий runtime age limit; fallback нужен для уже обнаруженных записей без `posted_at`. До admission и в циклах переводить все pending, включая записи вне рабочего набора, в terminal `skipped`; просроченные `claimed` закрывать только после истечения claim lease. `submitting` с неясным исходом не объявлять просроченным и сохранять защиту `unconfirmed`. Создавать/сохранять Reply с понятной причиной (A09). Строки комментариев и история попыток не удаляются.
- **Ошибки контекста:** ошибка fetch/save article context повторяет generation job с существующим cooldown; если контекст успешно получен, но текст статьи недоступен, сохраняется текущее поведение — генерация без него (A08). Иные ошибки этого этапа не должны теряться или молча превращаться в ответ без контекста.
- **Неопределённая публикация:** сохранить действующий fail-safe: если submit мог состояться, но подтверждение не пришло, закрыть publication как `unconfirmed`, не отправлять повторно.
- **Studio:** раз в пять минут, плюс немедленная короткая проверка на старте и досрочная при пустом активном окне (не чаще раза в минуту после последней попытки). Успешный досрочный scan сдвигает следующий плановый срок ещё на пять минут; неуспешная попытка повторяется через пять минут и не отменяет обработку очереди. Обновлять открытую вкладку Studio на месте, извлекать не более 100 верхних post cards и раскрывать доступные ответы. Поиск исходного комментария для публикации использует ту же ограниченную верхнюю выборку и не запускает отдельный глубокий проход; если комментарий там не найден, попытка остаётся retryable и не считается подтверждённым отсутствием (D01). При адаптере без short-scan метода не подменять его full scan (A12, A15).
- **Метрики:** `comments.fetched_at` сохраняет первое обнаружение, а `replies.published_at` фиксирует только подтверждённую публикацию. После запуска снять read-only запросами среднее/медиану от обнаружения до публикации, Reply `generated` с pending publication row в состояниях `queued`, `waiting`, `claimed` или `submitting`, и stale completions. Указать период и объём latency sample; при менее 30 публикациях или периоде короче 24 часов вывод о лимите 30 предварительный.
- **Релиз:** очистка Docker cache и добавление swap уже завершены на предыдущем релизе. Свежий backup обязателен до любого production schema update; если migration не нужна, данные и volume не трогать. Старый worker остановить до release, новый запустить после него.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Оркестратор | Порядок этапов и ограниченный drain, короткий scan schedule | `run_cycle()` | Due selection на уровне цикла, error continuation и расписание |
| AI providers/settings | Request timeout к моделям | `AI_REQUEST_TIMEOUT_SECONDS` и provider factory | HTTP клиент, retry connect и формирование запросов |
| Repository | Durable work window, admission, claim leases, quota reservations, retry, expiry reason | `reconcile_work_window(now, stale_before, limit) -> WorkWindowSnapshot` и текущие generation/publication methods | SQL, транзакции и переходы `waiting ↔ queued` |
| Studio adapter | Обновление текущей Studio page, short DOM scan и ответы | `fetch_recent_comments(max_cards=100)` | Навигация страницы, селекторы, прокрутка и раскрытие скрытых ответов |
| Production operations | Backup/rollout и разовое измерение после старта | Runbook plus read-only SQL | Host access и secrets |

Тестовые швы: `run_cycle()` с fake repository/page/provider; PostgreSQL repository tests для очереди, квоты и age expiration; AI provider tests для настраиваемого timeout (A10 — используем существующие seams, не создаём отдельный testing API). Тесты не публикуют реальные комментарии.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R03/R04 — повторно чистить хост, менять swap или RAM | Запрошенная очистка build cache и настройка swap уже выполнены; повторный системный cleanup не нужен для текущей логики очереди. |
| R05 — менять лимиты Chromium, RAM или добавлять хосты | Для требуемого code rollout этих изменений не нужно; это другая инфраструктурная задача. |
| R01 — отвечать на комментарии после действующего age limit | Ограничение возраста сохраняется; просроченные записи закрываются с причиной. |

## Открытые места

Открытое ограничение D01: production-поиск исходного комментария publication job сканировал 155–195 групп и 40 раз прокручивал Studio за 92–155 секунд, но проверил 0 кандидатов. Ticket 09 ограничивает этот путь той же верхней выборкой до 100 карточек и сохраняет retryable outcome при промахе. Остальные принятые параметры: `MAX_ACTIVE_WORK_ITEMS=30`; значения по умолчанию таймаута и лимита пачки описаны в assumptions A01–A02; Studio scan каждые 5 минут (или раньше при пустом окне, не чаще раза в минуту), верхние 100 карточек. Последнее уточнение пользователя отменяет глубокий проход. Если Studio page уже открыта, обновить её на месте; если закрыта, открыть Studio в той же аутентифицированной странице. Burst из более 100 новых карточек между удачными scans может выйти за пределы обнаружения короткого режима.

## Принятые технические допущения

- **A01 → R01.7:** default `AI_REQUEST_TIMEOUT_SECONDS=90` сохраняет текущий timeout GigaChat и применяет единое поведение к выбранному AI provider; оператор может изменить его настройкой.
- **A02 → R01.7:** использовать настроенный `MAX_REPLIES_PER_CYCLE` с default 10 из `.env.example` как реальный предел bounded drain вместо отдельного hard-coded числа.
- **A03 → R05/R06i:** перед схемным изменением production снять проверенный backup; запускать один worker только после миграции и проверить версию, heartbeat и целостность существующего PostgreSQL volume. Это safety-процедура выкладки на сервер с рабочими данными.
- **A04 → G06/G07:** оценка после запуска делается read-only запросами к production данным; не добавляется постоянный runtime отчёт.
- **A05 → R01.3/G04/G05:** repository предоставляет один транзакционный `reconcile_work_window` и immutable snapshot, чтобы атомарно выбрать jobs, вернуть счётчики окна и закрыть просрочку без промежуточного переполнения.
- **A06 → R01/G05/G06:** для age expiration использовать `posted_at`, а когда его нет — время первого обнаружения `fetched_at`; для latency брать первое обнаружение и только подтверждённое `published_at`. Это сохраняет понятный origin для записей, у которых публикационная дата не записана.
- **A07 → R01.3/G03/G04/G05:** вне рабочего набора использовать `waiting` в существующих полях queue, не удалять Comment/Reply и не сбрасывать retry history; это отделяет лимит активной работы от хранения и позволяет завершать просрочку с причиной.
- **A08 → R01.2/G02:** если чтение контекста успешно, но текст статьи не найден, оставить действующий режим генерации без текста; сетевые/сохранительные ошибки контекста при этом остаются retryable.
- **A09 → G05:** хранить краткую понятную строку причины истечения в `Reply.error_reason`, чтобы админка объясняла terminal status.
- **A10 → R01:** проверять поведение через текущие seams оркестратора, repository и provider; отдельный testing API не добавлять.
- **A11 → G07:** вывод о пригодности лимита делать после 30 подтверждённых публикаций и не менее 24 часов наблюдения; при меньшей выборке пометить оценку предварительной.
- **A12 → G01/G02:** при ошибке короткого Studio scan продолжать очередь и повторить scan по обычному 5-минутному расписанию.
- **A13 → R01.2/G02:** результат модели считается сохранённым только после успешной транзакции Reply + publication queue; при сбое БД повторить persistence того же текста, а если он утрачен до записи — заново выполнить generation.
- **A14 → R01.3/G04:** первая reconciliation допускает свежие legacy jobs в доступные слоты по свежести; после неё generation slots заполняются только из ещё не известных card IDs текущего scan. Остальные known generation jobs вне окна не реадмитятся, а ожидают явного age expiration. Так старый backlog не становится второй очередью после rollout.

- A15 → R01.3/G01/G02: лимит активного окна считает уникальные comment IDs, а не сумму queue rows; ранний успешный scan переносит следующий плановый срок на пять минут от себя, ошибка scan повторяется через пять минут и не останавливает очередь.
- A16 → R01.3/G04: `MAX_ACTIVE_WORK_ITEMS` задаётся переменной окружения, default равен 30, значение валидируется как положительное целое и применяется runtime reconciliation для ограничения активного окна. Ticket 06 создаёт настройку, Ticket 07 передаёт её в обработку.
