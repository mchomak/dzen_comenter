## Принятые за пользователя решения

- ASSUMPTION — обычная короткая проверка выполняется раз в 5 минут; при пустом активном окне досрочно, но минимум через 1 минуту после предыдущей попытки. Любая попытка переносит следующий срок на 5 минут; ошибка scan не останавливает очередь.
- ASSUMPTION — короткая проверка ограничена первыми 100 карточками и раскрывает доступные ответы.
- ASSUMPTION — лимит 30 включает уникальные comment IDs с active generation/publication работой, включая retry с будущим `next_attempt_at`; смена этапа не занимает второй слот.
- ASSUMPTION — publication jobs приоритетнее генерации; если их больше 30, они все остаются сохранёнными, а новые генерации ждут снижения этого хвоста.
- ASSUMPTION — действующий лимит возраста в один день сохраняется; если `posted_at` отсутствует, используется первое `fetched_at`.
- ASSUMPTION — новые комментарии располагаются сверху; burst из более чем 100 новых карточек между удачными короткими scan может остаться за пределами текущего поиска.
- ASSUMPTION — при первой reconciliation самые свежие legacy generation jobs могут занять свободные слоты; остальной старый хвост остается в `waiting` и по мере возраста явно завершается, не реадмитится. Новые свободные generation slots заполняются неизвестными карточками короткого скана; сохранённые replies получают publication priority.
- ASSUMPTION — раскрытие скрытых ответов в коротком Studio scan и публикационном source lookup ограничено 60 секундами на операцию; после срока scan возвращает уже видимые комментарии с признаком неполного раскрытия, а source lookup остаётся retryable.

## Технические допущения с привязкой к требованиям

- A01 → R01.7: default таймаута 90 секунд сохраняет текущий timeout GigaChat; настройка применяется к обоим AI providers.
- A02 → R01.7: настроенный `MAX_REPLIES_PER_CYCLE` (default 10 из `.env.example`) становится реальным пределом bounded drain вместо отдельного hard-coded числа.
- A03 → R05/R06i: backup, последовательный запуск одного worker и проверка health/schema/volume — процедура безопасной выкладки на production сервер с рабочими данными.
- A04 → G06/G07: запрошенные после запуска метрики снимаются read-only запросами, без отдельной постоянной отчётной функции.
- A05 → R01.3/G04/G05: единый транзакционный repository seam нужен для атомарного управления рабочим окном и просроченными jobs.
- A06 → R01/G05/G06: когда `posted_at` отсутствует, возраст берётся от первого обнаружения; latency заканчивается только подтверждённой публикацией.
- A07 → R01.3/G03/G04/G05: queue хранит неактивные строки в `waiting`, не удаляя комментарии и историю retry.
- A08 → R01.2/G02: при успешном fetch контекста без текста статьи сохраняется текущее поведение генерации без article text.
- A09 → G05: для terminal expiration хранится краткая понятная причина в `Reply.error_reason`.
- A10 → R01: тестирование использует текущие швы модулей без отдельного testing API.
- A11 → G07: вывод о лимите требует минимум 30 подтверждённых публикаций и 24 часа наблюдения; иначе он предварительный.
- A12 → G01/G02: ошибка короткого scan не останавливает очередь; повтор scan выполняется по штатному расписанию 5 минут.
- A13 → R01.2/G02: повторять persistence уже сгенерированного текста до success; генерацию повторять только если результат не удалось сохранить и он утрачен.
- A14 → R01.3/G04: при первом rollout выбрать самые свежие legacy jobs в свободные слоты; последующие слоты заполнять только новыми неизвестными IDs, старый хвост не реадмитить.
- A15 → R01.3/G01/G02: лимит активного окна считает уникальные comment IDs, а не сумму queue rows; ранний успешный scan переносит следующий плановый срок на пять минут от себя, ошибка scan повторяется через пять минут и не останавливает очередь.
- A16 → R01.3/G04: `MAX_ACTIVE_WORK_ITEMS` задаётся переменной окружения, default 30, валидируется как положительное целое и используется runtime reconciliation для ограничения активного окна; настройка создаётся в Ticket 06, подключение — в Ticket 07.
- A17 → G01: предел раскрытия скрытых ответов 60 секунд не позволяет короткой проверке зависнуть на длительном раскрытии; доступные комментарии сохраняются, оставшиеся ответы будут рассмотрены в следующем скане.
