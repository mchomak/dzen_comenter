# Спецификация: устойчивый поиск комментариев Studio

## Задача

При большой ленте Studio бот многократно проверяет уже просмотренные комментарии и раскрывает ответы в нерелевантных карточках. Это задерживает поиск, создаёт лишнюю нагрузку на Chromium и может остановить весь цикл. После падения страницы соединение с базой может не пережить запись статуса. При этом результат публикации должен оставаться безопасным от дублей.

## Решение

Поиск целевого комментария использует известную публикацию и обрабатывает только новые карточки между прокрутками. Ветки раскрываются только в карточках целевой публикации при публикационном поиске. Полный сбор ленты раскрывает элементы каждой карточки не более одного раза за проход. После подтверждённого падения Chromium сессия пересоздаётся сразу, а не ждёт планового keep-alive. Оба SQLAlchemy-движка проверяют соединение перед повторным использованием. Неопределённая отправка остаётся отдельным терминальным статусом, а исчерпанный поиск источника явно маркируется как ограниченный поиск, а не доказанное отсутствие.

## Решения по реализации

1. Сохранить синтетический ID комментария и существующие точные проверки DOM-контролов; использовать URL публикации из сохранённого Comment как дополнительную область поиска.
2. Для сохранения совместимости с историческими Comment без post_url оставить ограниченный fallback-поиск по ленте, но не пересматривать уже обработанные группы в одной серии прокрутки.
3. Классифицировать только известные ошибки renderer как основание немедленного восстановления. После восстановления текущий цикл завершается ошибкой и повторяется обычным расписанием; публикационный submit не повторяется, если его начало уже было отмечено.
4. Настроить pre-ping и recycle у общего фабричного SQLAlchemy engine, используемого worker и admin. Схему БД не менять.
5. Для поиска источника писать scan_limit_reached=true и absence_confirmed=false при исчерпании прокрутки. Оставить действующий конечный лимит публикационных повторов.
6. Диагностика не должна включать авторов, тексты, ссылки, токены или HTML. Фиксируются только безопасная фаза/причина, длительность, числа карточек, комментариев, элементов DOM и попыток; JS heap — только если показатель доступен.
7. Выпуск проверяется по фактически работающему коммиту и здоровью целевых контейнеров; схема/данные не меняются. Не запускать реальные действия отправки ответа для проверки — использовать подменённые браузерные/сетевые границы.
8. Отмечать цикл `in_progress` до его запуска и обновлять heartbeat после каждого прохода Studio и во время извлечения больших наборов комментариев. Healthcheck принимает только свежий progress heartbeat; остановившийся цикл остаётся stale.
9. На live Playwright Page извлекать post link/title и все поля комментариев одним read-only DOM-снимком. Синтетические ID и временные метки остаются вычислениями Python; fallback для fake DOM сохраняет тестируемый путь.
10. Исправить доказанный предел раскрытия ответов: production-лента обычно занимает 10–13 минут, а один проход — около 19 минут, при текущем общем сроке 10 минут. Установить общий предел 30 минут: он конечен и fail-closed с запасом над измеренным максимумом; прогресс раскрытия фиксируется по мере обработки каждой группы.
11. Если worker остаётся в `cycle_in_progress`, но не обновляет heartbeat 35 минут, он должен завершить процесс, чтобы `restart: unless-stopped` восстановил его. В штатном долгом проходе свежие heartbeat исключают ложные рестарты. Не выдавать stale heartbeat за прогресс и до выхода сохранить `unconfirmed` для начатой публикации, не возобновляя её автоматически.
12. Уточнить безопасные диагностические события/счётчики, достаточные отличить превышение ограниченного scan budget, изменение/исчезновение DOM-контрола, ошибку публикации и зависание цикла; сохранять действующие запреты на комментарии, авторов, URL и HTML в логах.
13. Для `control_target_changed`, `control_disappeared_before_click` и `publication_missing` разрешить один повторный поиск актуального элемента после повторной проверки идентичности публикации/ветки/контрола. `click_dispatch_ambiguous` сохранять как отказ от повторной отправки. Не изменять правильную fail-closed семантику, чтобы просто убрать сообщения об ошибке.
14. Для каждой зарегистрированной причины в итоговом production-срезе показать безопасный счётчик и статус обработки: исправлено, безопасно восстановлено или намеренно остановлено с причиной. Не считать одиночную ошибку БД доказательством сбоя пула; если повторный случай подтвердится после уже включённого pre-ping/recycle, локализовать конкретную операцию и восстановление соединения.
15. `TimeoutError` классифицировать по фазе и операции. Для чтения/keep-alive применять конечное число повторов, а подтверждённый сбой браузера передавать существующему восстановлению сессии; при истечении ожидания публикации сохранять `unconfirmed` без повторного submit. По единичному `OperationalError` без повторения или достоверного кода драйвера не делать более точного вывода, чем позволяют данные; зафиксировать неопределённость и безопасную диагностику следующего случая.

16. Перед завершением зависшего цикла supervisor должен получить потокобезопасный снимок активной попытки `{reply_id, claim_token}` из Orchestrator и синхронно сохранить существующий переход в `publication_unconfirmed`. Если БД недоступна, durable submitting claim остаётся non-retriable до штатного lease recovery; нельзя разрешать автоматический повтор. Не убивать только зависший поток и не обходить фиксацию небезопасным завершением процесса. Основание: D01.
17. После успешных проверок и review выполнить commit/deploy, затем проверить фактически работающий commit, здоровье app/admin/PostgreSQL и heartbeat бота. Не запускать реальную публикацию для проверки.
