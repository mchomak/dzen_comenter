# Аудит контекста статьи для GigaChat

Дата: 22 августа 2026. Режим: read-only, без запуска воркера и без запросов к GigaChat.

## Короткий вывод

Текст статьи **не сохраняется** в PostgreSQL после генерации. В `replies` записывается лишь `article_context_status` (`article_text_used` либо `without_article_text`), поэтому восстановить уже переданные модели тексты из БД нельзя.

Текущий путь отправляет модели весь `inner_text()` первого непустого DOM-контейнера: сначала `article`, затем `main`, затем элемент с классом, содержащим `article`. Это означает реальный риск получить вместе с текстом статьи навигацию, рекламу, рекомендации и комментарии, особенно при fallback на `main`. В текущем коде такие узлы не отфильтровываются и длина статьи не ограничивается.

## Что подтверждено

- `DzenStudioPage.fetch_article_text()` открывает статью в отдельной Playwright-вкладке и выбирает первый непустой селектор `article` → `main` → `[class*="article"]`.
- Для выбранного узла вызывается `inner_text()`: метод забирает весь дочерний текст контейнера без allowlist содержательных тегов и без исключения UI-блоков.
- `OrchestratorLoop` передаёт этот текст как `PromptContext.article_text`, а prompt builder добавляет его в секцию `Текст статьи` целиком.
- Таблица `replies` не имеет поля с текстом статьи или с token usage. Предыдущая read-only сверка production БД также показала только статусы использования контекста, а не сохранённые статьи.
- Регрессионная проверка затронутых модулей прошла: `87 passed`; полный локальный набор: `378 passed, 24 skipped`.

## Чего нельзя утверждать без живой выборки

Не установлен точный процент лишнего текста и нельзя назвать финальный лимит символов: для этого нужно прогнать несколько публичных текстовых URL из production БД через тот же `fetch_article_text()` и замерить selector, длину и состав результата. Такой read-only доступ сейчас невозможен: сервер не принимает ключевую аутентификацию, а пароль из переписки не используется.

Поэтому утверждение «в prompt точно попадают реклама/отзывы» пока является обоснованной гипотезой, а не измеренным фактом.

## Независимая сверка

Независимая проверка кода подтвердила тот же результат: сохранения article text и live-выборки URL нет, а очистки контекста до передачи в prompt нет. Её безопасная выборочная проверка — `7 passed, 80 deselected`; она использует фейки и поэтому не подменяет production-замер.

## Как исправить грамотно

1. Извлекать блоки по DOM, а не весь `main.inner_text()`: заголовок и элементы `h1`–`h3`, `p`, `li`, `blockquote`, `figcaption` в порядке страницы.
2. До извлечения исключать вложенные `nav`, `aside`, `footer`, `form`, `button`, а также блоки рекомендаций, комментариев и рекламные контейнеры по устойчивым data-атрибутам/классам, подтверждённым на живых страницах.
3. Сначала использовать `article`; если его нет, искать узкий content-root, а не отправлять весь `main`. Если надёжного body-root нет — вернуть пустой article context: это дешевле и безопаснее, чем слать chrome страницы.
4. После очистки ограничивать контекст на границе содержательного блока или предложения. Конкретный лимит выбрать по замерам выборки и зафиксировать тестами; не резать слово посередине и не выкидывать целиком длинный абзац.
5. Добавить telemetry на каждый вызов: selector, `article_chars_raw`, `article_chars_sent`, причина пропуска и provider `usage.prompt_tokens/completion_tokens/total_tokens`. Сам текст статьи не сохранять в production БД без отдельного решения по данным и доступу.

## Критерии для следующей безопасной проверки

- Сначала выбрать несколько URL только вида `https://dzen.ru/a/...` read-only запросом к БД.
- Для каждого URL получить текст точно методом `DzenStudioPage.fetch_article_text()` в изолированном браузерном контексте; не использовать HTTP-парсер как замену.
- Зафиксировать только обезличенные метрики: selector, число символов до/после очистки, категории исключённого UI и несколько коротких технических примеров без комментариев пользователей.
- Не запускать воркер, не публиковать ответы и не вызывать GigaChat.
