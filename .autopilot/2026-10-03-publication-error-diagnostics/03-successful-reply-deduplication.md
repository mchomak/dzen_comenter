# 03 — Дедупликация только после успешной публикации

**Требования:** G07
**Blocked by:** none
**Зона:** `dzen_commenter/orchestrator/`, `dzen_commenter/dzen/`, `tests/orchestrator/`, `tests/dzen/`
**Волна:** 1
**Status:** done

## Что должно заработать

На каждом сохранённом комментарии worker явно спрашивает существующий repository, есть ли опубликованный ответ для его DB comment id. При положительном результате он пропускает комментарий до запуска следующей генерации. Если опубликованного ответа нет, комментарий не классифицируется как успешно обработанный и остаётся на существующем пути очереди и ограниченных повторов. Перед повторным submit браузерный путь дольше ищет уже появившийся ответ, чтобы задержка публичного UI не создала второй ответ.

## Из брифа, дословно

> «когда бот получает новый комментарий, нужно котрыть БД и посикать был ли там такой же комментарий, если был и мы уже успешно на него ответили, то его проупстить, если не был, или мы не смоли опубликовать ответ, то работаем»

§§9.2–9.3.

## Критерии приёмки

- [x] Для сохранённого eligible-комментария вызывается `has_published_reply(comment_id)`.
- [x] Если repository сообщает о опубликованном ответе, новая генерация/публикация для этого comment id не запускается.
- [x] Если ответ ещё не опубликован, intake не помечает комментарий как успешно дедуплицированный и оставляет его текущему bounded queue/retry flow.
- [x] Предварительный поиск публичного ответа ждёт до 10 секунд; fake-page test показывает, что ответ, появившийся после прежнего двухсекундного окна, предотвращает повторный submit.
- [x] Регрессионный тест сначала воспроизводит отсутствие DB lookup, затем проходит после реализации; тесты используют fake repository и не подключаются к PostgreSQL.
