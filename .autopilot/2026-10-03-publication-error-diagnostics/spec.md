# Спецификация: диагностика ошибок публикации

## 1. Цель и границы

Улучшить диагностические логи существующего браузерного пути Дзена так, чтобы по production-логам было понятно, на каком шаге и почему обработка остановилась: чтение ленты и извлечение комментариев из Студии, открытие статьи и чтение её текста, поиск исходного комментария, загрузка/сортировка публичных комментариев, раскрытие ветки, поиск элементов управления или подтверждение опубликованного ответа.

Поведение публикации, подтверждение результата, число попыток, durable queue и состояния комментария остаются прежними. Сбор логов не должен требовать реального входа или запросов к Дзэну.

## 2. Требования к диагностике — R01

### 2.1 События и поля

На существующих границах Dzen browser adapter (`dzen_commenter/dzen/page.py`) логировать завершение и неуспех с именем действия и устойчивой причиной. Для ошибок сохранять `failure_stage`, `failure_reason`, тип исключения и безопасное краткое описание исключения. Сохранять доступные числовые сведения, объясняющие поиск/загрузку: число карточек публикаций и извлечённых комментариев, пропуски карточек без ссылки, длина извлечённого текста статьи (без самого текста), число найденных карточек/веток, число проверенных кандидатов, число попыток навигации, результат навигации/HTTP status, число ожиданий загрузки и число раскрытых веток/нажатий «загрузить ещё».

События должны различать как минимум: страницу Студии не удалось прочитать; карточка публикации пропущена, так как ссылка не распознана; переход на статью завершился исключением или неуспешным HTTP status; текст статьи не найден/не загрузился; публичные комментарии не загрузились за отведённое ожидание; исходный комментарий не найден после исчерпания поиска; ветка/дополнительные комментарии не раскрылись; кнопка ответа/отправки или поле ввода не найдены; отправка завершилась исключением; опубликованный ответ не подтверждён.

Использовать уже существующий структурированный logger и его event naming; не вводить отдельное хранилище, новый канал доставки или новый слой логирования. При успешном шаге оставить компактные существующие lifecycle-события, добавив только полезные счётчики, которых пока не хватает.

### 2.2 Безопасность и приватность

Логи не содержат текст комментария/ответа/статьи, имена авторов, cookies, токены, логин/пароль, полный URL, query string, fragment или значения полей авторизации. Если нужно указать страницу, записывать только безопасный hostname и путь без query/fragment, либо существующее безопасное обозначение страницы. Исключение проходит через общий sanitizer: обрезается до разумного размера и удаляются URL query/fragment и возможные секретные значения. Не включать исходный traceback publication exceptions, так как существующая политика StructuredFormatter специально исключает потенциально чувствительные данные.

Записи об одном исходном действии коррелируются безопасным идентификатором уже имеющейся попытки/поста, если он доступен; не создавать новый идентификатор из текста комментария и не логировать синтетический comment id, если он раскрывает хеш пользовательских данных.

### 2.3 Сохранение поведения

Для исходного диагностического требования R01 добавление логов не меняет типы повторов, тексты, таймауты, условия успешности, клики, порядок публикации, результаты извлечения комментариев/статьи и durable queue. Ошибка остаётся той же ошибкой для вызывающего кода, кроме безопасно более точного сообщения, если оно не используется как control value. Telegram-уведомления и форматирование остальных логов не меняются. Более позднее требование G07 явно меняет только окно public preflight по §9.2; оно имеет приоритет для этого изменения.

## 3. Запрет операций с БД — R03

Запрет R03 касается прямых операций развёртывания с данными и схемой: не выполнять вручную SQL, `alembic`, backup/restore или очистку данных. Чтобы удовлетворить R02 без запуска миграции во время такого deploy, как реализационное решение добавить узкое переключение: по умолчанию текущая миграционная команда работает как прежде, а при `RUN_DB_MIGRATIONS=false` entrypoint пропускает её и запускает приложение. В deploy-команде явно выставить `RUN_DB_MIGRATIONS=false`. Позже пользователь прямо заказал штатный runtime lookup существующего ответа в G07; он не означает ручную DB-операцию или изменение схемы.

Для исходного запроса «БД не трогай» означает: не подключаться к production для SQL, не запускать Alembic, не менять/не удалять схему и данные, не делать backup/restore и не перезапускать/пересоздавать сервис PostgreSQL. Обычные DB-вызовы работающего приложения сохраняются; более поздний G07 явно просит добавить runtime lookup по существующей repository границе.

## 4. Commit, push и redeploy — R02

Для исходных изменений R01/R02 выполнены проектная проверка, commit/push и redeploy только worker service `app` из canonical deployment checkout; перед стартом проверены путь, ветка и контейнер, после — health и app logs. PostgreSQL/admin не перезапускались, DB-команды и миграции вручную не запускались. R02 этой части закрыт commit `291bad5`. Новый Ticket 03 относится к добавлению G07 и остаётся локальным; его production deploy не подразумевается без отдельного указания.

## 5. Тестирование

- Добавить/обновить unit-тесты с fake Playwright pages на диагностические ветки: пустая/непрочитанная лента Студии, карточка без распознанной ссылки, ошибка перехода/пустой текст статьи, не загрузившийся список комментариев, ненайденный источник и отсутствие кнопки/подтверждения.
- Проверить, что ожидаемые `failure_stage`/`failure_reason`, безопасные счётчики и тип исключения попадают в structured log, а чувствительные тексты/URL query не попадают.
- Проверить entrypoint: миграция выполняется при отсутствии переменной и при `true`, пропускается при `false`, затем приложение запускается.
- Запустить затронутые тесты и доступный полный локальный набор. Не запускать реальный браузер Дзена или внешние запросы к нему.

## 6. Вне объёма

- Изменение логики сбора новых комментариев, извлечения текста статьи, генерации LLM-ответов, авторизации и публикации.
- Изменение Telegram/email уведомлений, health semantics, runtime-конфига или панели.
- Изменение схемы, данных, миграций, DB connection settings или контейнера PostgreSQL.
- Ручное тестирование на реальном аккаунте/страницах Дзена.

## 7. Границы реализации

- `DzenStudioPage` в `dzen_commenter/dzen/page.py` владеет событиями чтения ленты/комментариев, извлечения текста статьи и публикации/публичной проверки. Его существующие методы остаются интерфейсом; новые публичные методы и изменения моделей/контрактов не нужны.
- Ошибки Playwright тестируются через уже существующие fake page/browser швы в `tests/dzen/test_dzen_page.py`; формат JSON тестируется существующим `StructuredFormatter` из `dzen_commenter/monitoring/logging_config.py`. Сырые publication tracebacks остаются выключены.
- `docker/entrypoint.sh` владеет условным запуском Alembic: `RUN_DB_MIGRATIONS` по умолчанию включает текущий `alembic upgrade head`; ровно значение `false` отключает его. `docker-compose.yml` передаёт переменную в сервис `app`, чтобы deploy мог задать false через окружение.
- Entrypoint проверяется fake `alembic` executable в `tests/test_entrypoint.py`; передачу Compose-переменной проверяет `tests/test_admin_app_import.py` либо профильный compose test. Тесты не подключаются к PostgreSQL.
- Рабочая среда: Python 3.11, Playwright fake pages, Docker Compose. Команда тестов: `.venv\\Scripts\\python.exe -m pytest -q`; полноценный Docker runtime требует Docker/Compose.
- Нельзя трогать PostgreSQL-сервис, данные, миграции, модели или репозиторий; не устанавливать зависимости автоматически; не обращаться к реальному Дзэну.

## 8. Обоснование размера

Tier T1: это одна поставка диагностики браузерного пути Дзена и два раздельных участка владения — адаптер/его fake-page тесты и Docker entrypoint/Compose gate с собственными тестами. Они не делят файлы и могут разрабатываться независимо; DB-запретный gate обязателен для безопасного production redeploy этой же поставки.

### 8.1 Решения реализации для исходных R01–R03

Следующие пункты — ограничения реализации, выбранные для выполнения исходного запроса на диагностику/безопасный deploy, а не отдельные пользовательские возможности:

- Логи санитизируют исключения и не содержат пользовательский текст/личность, credentials, полный URL или сырые publication tracebacks: диагностика не должна раскрывать данные.
- Логи и браузерный путь проверяются fake Playwright/repository объектами; тесты не делают production-запросов и не требуют реальной авторизации.
- Миграционный gate и ограничение redeploy только контейнером `app` позволяют выполнить запрошенный redeploy без прямого воздействия на БД.

## 9. Дополнение от 2026-10-04: причины ошибок и защита от повторных ответов

### 9.1 Диагностика публикаций

- Итоговый отчёт сверяет сохранённую выгрузку ошибок, агрегаты production-логов за последние 12 часов и код публикации. Числа из повторяющихся lifecycle-событий отдельно не выдаются за число уникальных комментариев.
- Для каждой причины, которую подтверждают сохранённые поля, отчёт даёт практическое действие. По каждой иной группе он указывает, что имеющейся записи не хватает для атрибуции, какие поля/события отсутствуют и что проверить при следующем сбое; отчёт не приписывает конкретную причину строкам, где доказательств нет.
- Проверка кода подтверждает, что точный статус create API сохраняется в мутационной трассе: любой не-2xx (включая 3xx/4xx/5xx) классифицируется как `creation_outcome=non_2xx`. Ответ 2xx с кодом не 200 не является HTTP-отказом; публикацию всё равно подтверждают только отдельные признаки в Студии и публичной ветке.
- Отчёт явно разделяет доказанные причины и неполноту телеметрии. Отсутствие non-2xx в сохранённых response trace не означает, что таких отказов не было в событиях без сохранённого response.
- Серверные перезапуски или увеличение ресурсов рекомендуются только при подтверждённых ресурсных/процессных симптомах. Код и серверные параметры для этого отчёта автоматически не меняются.

### 9.2 Идентичность комментария и успешная дедупликация — G07

- Текущая durable-идентичность комментария — уникальный `dzen_comment_id`, синтетически полученный из ссылки публикации, ссылки автора и текста. Повтор с тем же ID обновляет существующую запись, а не создаёт новую.
- После upsert воркер явно проверяет в существующей БД `has_published_reply(comment_id)`. Если успешный ответ уже есть, обработка этого комментария прекращается до следующей генерации.
- Отсутствие опубликованного ответа не считается дубликатом-успехом: комментарий остаётся на существующем пути генерации или повторной публикации. Существующие cooldown и максимум попыток сохраняются; исчерпавшая лимит terminal error не должна бесконечно сбрасывать очередь при каждом опросе.
- Перед повторным нажатием публикации адаптер продолжает искать уже видимый ответ по исходной ветке, автору бота и точному нормализованному тексту. Окно этой публичной проверки увеличивается с текущих 2 секунд до 10 секунд, чтобы совпасть с последующей проверкой подтверждения и уменьшить риск повторного submit при задержке отображения.
- На этой поставке нет изменения схемы/миграций, ручного SQL, прямого доступа к production БД, перезапуска контейнеров, изменения серверных retry settings или реальной авторизации/публикации в Дзене. Приложение использует только штатные репозиторные чтения и записи, уже нужные рабочему циклу.
- §4 описывает завершённый 2026-10-03 rollout диагностики по R02. Новый Ticket 03 выполняется локально; его push/deploy не входит в это дополнение и не перезапускает production-контейнер.

### 9.5 План поставки

Это один T1 этап: явный DB guard и расширенное окно preflight вместе закрывают один сценарий повторной публикации. Их отдельные tickets добавили бы второй контекст и отдельные точки commit/review без независимой демонстрации результата, поэтому они объединены в Ticket 03.

### 9.3 Критерии приёмки

- Fake-repository тест показывает, что при наличии уже опубликованного ответа lookup выполняется и новая генерация не запускается; для непубликованного комментария lookup не классифицирует запись как успешную.
- Fake-page тест показывает, что ответ, появившийся в публичной ветке позже текущего двухсекундного окна, обнаруживается в увеличенном окне и не вызывает повторный клик.
- Существующий тестовый ответ HTTP 403 остаётся `non_2xx`; успешный API-ответ без положительного UI-доказательства не становится `published`.
- Рекомендации по таймаутам, числу повторов и рестартам опираются на раздельные данные выгрузки/логов и не требуют неподтверждённых настроек сервера.
