# Спецификация: аудит расхода токенов GigaChat

## Задача

Заказчик израсходовал заявленные 50 000 000 токенов GigaChat-Pro (модель требует подтверждения) приблизительно за месяц и должен остановить дальнейшие списания до поступления новой покупки. Нужен отчёт, который отделяет подтверждённые цифры от предположений и даёт применимый план снижения расхода.

## Решение

Провести безвредный аудит в двух слоях: статический анализ репозитория и, если доступен безопасный SSH-доступ без применения пароля из переписки, read-only анализ развёрнутого окружения и PostgreSQL. Остановить только точно идентифицированный воркер после проверки способа развёртывания; при отсутствии такого доступа явно зафиксировать невыполненное аварийное действие и безопасный следующий шаг. Итог — краткий отчёт с расчётами, вероятными источниками расхода и ранжированными мерами.

## Решения по реализации

- Источник правды для фактического расхода — биллинг провайдера, затем серверные логи и агрегаты PostgreSQL. БД приложения может не хранить usage-токены, поэтому отсутствие поля usage не является доказательством отсутствия списаний.
- Безопасная аутентификация — только уже настроенный SSH-ключ/сертификат. Пароль, переданный в переписке, не используется; он не записывается в файлы, команды и отчёт.
- Статический анализ следует существующим швам: `OrchestratorLoop`, prompt builder, AI factory/adapters, runtime config и SQLAlchemy repository. Это показывает максимальную частоту вызовов, размер prompt и параметры генерации без обращения к внешнему API.
- Серверная остановка — только после проверки `systemctl` и Docker Compose. Не выполнять широкие `kill`, изменения firewall, миграции, удаление профилей или SQL-команды записи.

### Ограничение доступа

Переданный в переписке пароль root не является допустимым способом подключения: он уже скомпрометирован и не будет применён. Проверка настроенного SSH-доступа по ключу к указанному серверу завершилась отказом. Это не отменяет R05–R06: для их выполнения требуется безопасный уже настроенный доступ, после чего аудит остаётся read-only, а остановка выполняется только для идентифицированного воркера. Пароль следует немедленно заменить.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Статический аудит | оценкой возможного расхода из кода | перечень вызовов, лимитов и размеров контекста | любые учётные данные и реальные сетевые запросы |
| Read-only серверный аудит | состоянием развёртывания и агрегатами БД | измеренные объёмы, периоды и статус воркера | содержимое комментариев и секреты окружения |
| Отчёт | сопоставлением фактов, гипотез и мер | рекомендации и порядок действий | неподтверждённые выводы как «факты» |

Шов для проверки — существующие unit-тесты и публичные методы `OrchestratorLoop`, prompt builders и AI client adapters; новый production-код не создаётся.

## Открытые места

- Нужен доступ через SSH-ключ/сертификат либо иной уже настроенный безопасный канал, чтобы подтвердить состояние воркера и получить read-only агрегаты БД.
- Нужна выгрузка usage из кабинета GigaChat, чтобы соотнести billed input/output/cache tokens с приложением и подтвердить модель.
