# Отчёт: расход токенов GigaChat

Дата: 2026-08-21. Источники: статический анализ текущего репозитория, точечный тестовый прогон и официальная документация GigaChat. Сервер и PostgreSQL не исследованы: аутентификация по уже настроенному SSH-ключу отклонена, а пароль из переписки не используется.

## Итог

Наиболее вероятная причина быстрого исчерпания пакета — сочетание неограниченной генерации в режиме черновиков, тяжёлого и неограниченного входного контекста и завышенного лимита ответа. Код не сохраняет `usage` ответа GigaChat, поэтому точное разложение уже потраченных токенов из имеющейся БД невозможно.

Бот не остановлен: его статус на сервере неизвестен без безопасного доступа. Пароль root, попавший в переписку, нужно заменить. Это статический аудит, а не доказанный биллинг-анализ.

## Проверенные факты

| Факт | Доказательство | Последствие |
|---|---|---|
| Лимит `max_comments_per_hour` считает только ответы со статусом `published`. | `OrchestratorLoop.run_cycle` вызывает `count_published_replies_since`; репозиторий считает только `PUBLISHED`. | При `auto_publish=false` черновики имеют `GENERATED`, поэтому почасовой лимит не ограничивает вызовы модели. |
| Настройки по умолчанию: 10 генераций за цикл, цикл 60 секунд, `AI_MAX_TOKENS=512`. | `runtime_config.py` и `.env.example`. | Теоретический потолок при черновиках — 600 запросов/час, 14 400/сутки; только максимальный output — 7 372 800 токенов/сутки. |
| В каждый запрос передаются полный текст статьи и ветка комментариев без лимита длины. | `loop.py` получает `fetch_article_text`, `builder.py` добавляет `article_text` и `thread_text`. | Один и тот же длинный текст статьи может оплачиваться многократно для комментариев одной публикации. |
| Даже минимальный стандартный prompt занимает 1 109 символов, без статьи и ветки. | Вычислено кодом из текущих default-констант. | По ориентиру провайдера 3–4 символа на токен это примерно 277–370 токенов ещё до переменного контекста и ответа; фактическую тарификацию подтверждает только `usage`. |
| Ограничение длины ответа добавляется в prompt только для CTA-кандидата. | В `loop.py` инструкция «Длина ответа» находится внутри `if cta_instruction`. | Для обычного ответа модель может использовать все 512 output-токенов. |
| Слишком длинный ответ вызывает второй полный запрос с тем же prompt. | `loop.py`; тест `test_run_cycle_regenerates_once_when_reply_is_too_long`. | Один комментарий способен потратить бюджет двух генераций. |
| Адаптер GigaChat делает до трёх HTTP-попыток при 502 и повторяет completion после 401. | `gigachat.py`. | При неоднозначной сетевой ошибке возможны дополнительные обращения; без метрик их нельзя отделить от полезных запросов. |
| В таблице `replies` нет input/output/total tokens или числа попыток. | `db/models.py`, `repository.py`; адаптер берёт только `choices[0].message.content`. | Исторический отчёт по БД даст число сохранённых ответов, но не фактические списания и не все API-вызовы. |
| Для GigaChat фактическая модель берётся из `GIGACHAT_MODEL`, а в `replies.ai_model` записывается `AI_MODEL`. | `ai/factory.py`, `loop.py`. | Группировка БД по `ai_model` может ошибочно подписать реальную модель; модель нужно сверять с окружением и кабинетом. |

## Расчёт масштаба

- 50 000 000 токенов за 30 дней = 1 666 667 токенов/сутки.
- При 14 400 запросах/сутки среднее для такого расхода — только 115,74 тарифицируемого токена на запрос.
- Поэтому даже часть теоретического потока способна исчерпать пакет за месяц: фактический минимум зависит от числа новых комментариев, длины статьи/ветки, cache hit и ответов модели.

Числа рассчитаны программно. Это не утверждение о реальном числе запросов: подтверждение даст `usage.total_tokens` в API и кабинет провайдера.

## Что сделать сейчас

1. На сервере с корректным доступом перейти в каталог deployment и выполнить `docker compose stop app`, затем `docker compose ps app`. Это останавливает только воркер `app`, не удаляя БД, тома или панель. Не использовать `down`.
2. Заменить пароль root, который был отправлен в переписку; подключаться далее только ключом/сертификатом или другим защищённым каналом.
3. В кабинете GigaChat сохранить usage за последние 31 день и текущий баланс. Официальная документация указывает, что в ответе `chat/completions` есть `prompt_tokens`, `completion_tokens`, `precached_prompt_tokens`, `total_tokens`; это единственный источник точной тарификации по каждому вызову.

## Ранжированный план оптимизации

| Приоритет | Мера | Ожидаемый эффект | Риск качества / сложность |
|---|---|---|---|
| P0 | Ввести отдельный лимит генераций за час/сутки, считающий `GENERATED` и `PUBLISHED`, до вызова модели. Начать с малого консервативного лимита и алертов 60/80/90% дневного бюджета. | Устраняет неконтролируемый поток в режиме черновиков. | Низкий / низкая. |
| P0 | Всегда передавать целевую длину ответа и снизить `AI_MAX_TOKENS`; подобрать значение на репрезентативной выборке, а не оставлять 512. | Снижает output и почти убирает второй вызов из-за переполнения. | Средний / низкая. |
| P0 | Убрать второй LLM-вызов для слишком длинного ответа: безопасно обрезать до предложения либо сохранять как требующий ручной правки. | Убирает до 50% расходов на затронутых комментариях. | Низкий–средний / низкая. |
| P1 | Ограничить `article_text` и `thread_text` по символам/токенам; для статьи передавать релевантный фрагмент, не полный текст. | Основное снижение input-токенов на длинных статьях и ветках. | Средний / средняя. |
| P1 | Перед API выносить локальные правила «пропуск»: запрещённые темы, пустые/слишком длинные/явно спамные комментарии. | Не тратит модель на ответы, которые prompt всё равно велит пропустить. | Низкий / средняя. |
| P1 | Сохранять telemetry каждого API-вызова: timestamp, фактическая модель, причина (`initial`, `regenerate`, `retry`), `prompt_tokens`, `completion_tokens`, `precached_prompt_tokens`, `total_tokens`, статус. Не сохранять prompt и текст комментария в метриках. | Делает будущий расход объяснимым и позволяет установить лимиты по реальным данным. | Низкий / средняя. |
| P2 | Для повторяемой неизменной инструкции проверить cache hit по `precached_prompt_tokens`; группировать стабильные правила одинаково и сравнить с контрольным периодом. | Может уменьшить оплачиваемый повторяющийся input. | Низкий / средняя. |
| P2 | Проанализировать 502/401 по telemetry и не повторять completion после неоднозначного ответа без idempotency-стратегии, подтверждённой провайдером. | Снижает возможные дубликаты. | Средний / средняя. |

## Что запросить read-only после восстановления доступа

1. Статус deployment (`docker compose ps`) и безопасно остановить только `app`.
2. Активный `runtime_config.json`: `auto_publish`, `max_comments_per_hour`, `max_reply_length`, CTA; не выводить секреты `.env`.
3. Агрегаты PostgreSQL по дням, `ai_provider`, сохранённому `ai_model`, `status`, числу ответов, длине `generated_text` и `error_reason`.
4. Отдельно посчитать ошибки `reply too long after regeneration`: это нижняя граница подтверждённых двойных генераций.
5. Сопоставить эти агрегаты с выгрузкой GigaChat usage. БД не содержит usage, поэтому она не должна использоваться как единственный биллинг-источник.

## Внешние источники

- Официальные тарифы для юрлиц: пакет 50 000 000 токенов GigaChat Pro за 25 000 ₽ и идентификаторы `GigaChat-Pro` / `GigaChat-2-Pro`.
- Официальный подсчёт токенов: тарифицируются вход и ответ; `usage` содержит billed total и cache-поля.

## Слепая приёмка

Независимая проверка подтвердила целевой тестовый набор (`80 passed`), но ожидаемо не нашла реального серверного аудита и остановки воркера. Эти два пункта остаются невыполненными до появления безопасного доступа.
