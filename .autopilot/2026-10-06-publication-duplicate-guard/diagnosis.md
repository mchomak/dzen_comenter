# Диагностика тройного ответа, 6 октября 2026

## Показанный случай

Показанный комментарий найден по снимку в production БД: `comments.id=3865452`, связанный `replies.id=8869`. Ответ создан в БД 4 октября в 08:24 по Москве; дата «5 октября» из сообщения была приблизительной. В БД ровно один сгенерированный ответ для комментария; очередь зафиксировала `attempt_count=3` и завершилась ошибкой `reply not confirmed in public article`. Текст ответа имеет длину 430 символов. Времена каждой попытки в БД не хранятся. Журнал приложения за ранний период этого ответа недоступен, поэтому точное число HTTP create и распределение видимых дублей по попыткам не доказаны.

## Подтверждённый аналог из журнала 5 октября

У другого ответа `reply_id=9003` в каждой из трёх попыток журнал фиксирует `response_outcome=accepted`, затем `publication_studio_visibility_check` с `reply_visible=true`, затем `publication_article_verification_failed/reply_not_confirmed`. Первая попытка: 03:52:44–03:53:17 UTC; вторая: 04:53:23–04:53:54 UTC; третья: 05:54:25–05:55:02 UTC. Очередь выполнила retry после двух первых проверок и завершила третью как terminal. Это прямое доказательство, что принятый сайтом create может ошибочно трактоваться как неуспех публикации и приводить к следующему submit.

## Retry и повторный click

В активном production контейнере используется release `c76af81`, runtime cooldown 60 минут, максимум 3 попытки. В журнале 5 октября — 93 уникальных publication jobs и 100 интервалов между повторными claims; минимум 3605.923375 секунды, 0 интервалов меньше 3600 секунд. Значит, обычный cooldown действительно соблюдается. С 4 октября 13:16 UTC журнал содержит 175 событий `publication_send_click_attempt` с `attempt=1`, ни одного с `attempt=2`; второй click — реальный путь в коде, но для виденного инцидента он не доказан.

## Почему БД не спасла от повторов

`comments.dzen_comment_id` уникален, у найденного комментария ровно один reply. `complete_publication` обновляет reply, comment и queue атомарно только после Studio и public confirmation. Когда сайт принимает create, но public check не находит ответ, `fail_publication` атомарно сохраняет `publication_retry`, а затем `publication_error`; `has_published_reply` закономерно возвращает false. Отсутствия записи комментария или ответа в БД для найденного инцидента нет. Ошибка — в классификации принятого, но неподтверждённого submit как повторяемой неудачи.

## Ресурсы сервера

Сервер: RAM 1967 MiB, available 365 MiB, swap 255/255 MiB, контейнер app 1.296 GiB RAM; диск `/` 29 GiB, свободно 15 GiB. Нехватка RAM может замедлять браузер и появление DOM, но не меняет установленную причинную цепочку accepted create → confirmation failure → retry.
