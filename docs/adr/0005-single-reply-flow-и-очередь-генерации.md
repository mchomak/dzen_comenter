# Контекст

Batch-обработка добавила отдельный формат нескольких ответов, накопление неполного batch и самостоятельный execution path. Историческое исследование зафиксировало стабильную pre-batch выборку (`5eab5ff`: 140,51 часа, 761 reply, 0 `ReplyError`), а после batch появились ошибки разбора и попадание служебных маркеров в публичный текст. Владельцу нужен прозрачный путь для одного комментария без повторной генерации после browser/DOM-сбоя.

# Решение

Активная обработка использует один комментарий на один AI-вызов. Eligible comment атомарно создаёт или сохраняет одну job в `reply_generation_queue`; успешная генерация атомарно сохраняет reply и job в существующей `reply_publication_queue`. Очереди имеют раздельные cooldown и лимит попыток: generation retry повторяет AI, publication retry повторяет только сохранённый текст.

`SKIP` является единственным terminal control outcome модели. Ошибки генерации и публикации не становятся `skipped`; они оставляют фазовый статус и последнюю техническую причину. Claim обеих очередей получает opaque token, а complete/fail условно обновляют запись только при совпадении token, поэтому просроченный worker не может завершить lease, повторно занятый другим worker.

Batch runtime/admin settings, public repository API, prompt protocol и orchestration path удалены. Существующие batch-таблицы и записи (`reply_batches`, `comment_batch_queue`, `reply_batch_items`) сохраняются как исторические production-данные: новая миграция add-only создаёт generation queue и не удаляет либо не переписывает старые данные.

# Почему

Такой путь устраняет зависимость качества и диагностики отдельного комментария от формата нескольких элементов, сохраняет уже оплаченный AI-результат при сбое публикации и делает retry-намерение наблюдаемым по статусу. Сохранение исторических таблиц не требует рискованной миграции и оставляет возможность анализа старых инцидентов.

# Последствия и rollout

Переходящие `new` eligible-комментарии подхватываются из БД, поэтому не зависят от повторного присутствия в DOM. Batch-записи не обрабатываются новым кодом и не удаляются.

Перед production-миграцией обязателен свежий timestamped `pg_dump -Fc` с успешной проверкой `pg_restore --list`. После deploy проверяются compose health, migration/startup logs, отсутствие batch-настроек в active runtime config и read-only DB smoke query. При ошибке backup или миграции rollout останавливается; восстановление выполняется только по отдельному указанию пользователя.
