# Контекст

Для генерации ответа нужен текст статьи, а попытка публикации через браузер может завершиться ошибкой уже после успешной генерации. Повторная генерация в ответ на такую ошибку расходует AI-квоту и смешивает две разные неисправности.

# Решение

Контекст статьи хранится аддитивно у существующей `publications`, которая уже владеет идентичностью статьи: nullable-поля текста, времени получения, хеша содержимого и статуса контекста. При отсутствии cache сервис получает текст существующим парсером, сохраняет его и продолжает с безопасным пустым контекстом при ошибке получения.

Для готовых ответов создаётся отдельная durable publication-очередь с одним активным элементом на reply, состоянием, числом попыток, временем следующей попытки, последней ошибкой и временем claim. Ошибка поиска комментария в DOM или ошибка браузера переводит только этот элемент в retry с отдельными live-настройками cooldown и лимита попыток. После исчерпания попыток reply и comment получают `error` с причиной, но никогда не `skipped`.

Отклонённые альтернативы: отдельная таблица-копия статьи и повторный AI-вызов либо `skipped` при ошибке публикации. Первая дублирует URL и заголовок без нового владельца идентичности; вторая теряет диагностику, смешивает публикацию с генерацией и может необоснованно расходовать AI-квоту.

# Почему

Единый владелец контекста исключает рассинхронизацию статьи. Независимые очереди отделяют надёжную генерацию от менее надёжного DOM-действия, дают наблюдаемый retry и не блокируют остальные batch-процессы.

# Последствия

Миграция может быть только add-only: новые nullable-поля, таблица и индексы без удаления, обновления или переназначения существующих production-строк. Перед production-миграцией обязателен проверяемый timestamped `pg_dump -Fc`; при ошибке backup или миграции deploy останавливается, а восстановление выполняется только по отдельному указанию пользователя.
