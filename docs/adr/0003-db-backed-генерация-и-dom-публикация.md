# Контекст

Комментарии могут исчезать из текущего DOM-снимка Дзена уже после того, как сервис сохранил их в PostgreSQL. Привязка пакетной генерации к этому снимку превращала техническую недоступность DOM в терминальный `skipped`, хотя данные комментария уже были доступны сервису.

# Решение

Планирование и генерация пакетных ответов выполняются исключительно по сохранённым данным PostgreSQL. `comments.status = new` остаётся бизнес-состоянием ожидающего комментария, а `comment_batch_queue.state = queued` — техническим состоянием очереди; отдельный дублирующий статус `wait` не вводится.

DOM используется только в фазе фактического ввода и публикации уже сгенерированного ответа. Пакеты формируются по публикации: полный пакет берётся при достижении `batch_max_comments`, неполный — после `batch_wait_hours`. Claim и блокировки остаются транзакционными с `FOR UPDATE SKIP LOCKED`.

Отклонённая альтернатива: проверять наличие каждого комментария в текущем DOM перед генерацией и помечать отсутствующий как `skipped`. Она была отклонена, потому что временное отсутствие DOM не является бизнес-причиной пропуска и теряет возможность сформировать ответ из уже сохранённых данных.

# Почему

PostgreSQL даёт устойчивую очередь, детерминированную группировку и независимость генерации от краткоживущего снимка браузера. DOM остаётся необходимым только там, где без него нельзя выполнить действие в интерфейсе Дзена.

# Последствия

Сервис генерирует и сохраняет корректные ответы, даже если комментарий временно не виден браузеру. Он не обещает физическую публикацию для комментария, который Дзен окончательно больше не показывает: для неё требуется подтверждённый нативный идентификатор или permalink, которые в этом изменении не добавляются. Лимиты одного цикла и часовая AI-квота сохраняются.
