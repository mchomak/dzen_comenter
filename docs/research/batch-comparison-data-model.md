# Что можно честно сравнить: batch и одиночная генерация

Дата исследования: 2026-09-15. Источники — только история и исходный код этого
репозитория; production-БД, логи и конфигурация в этом исследовании не читались.

## Граница режимов

| Событие | Дата / коммит | Что это означает для данных |
|---|---|---|
| `comments.fetched_at` перестал перезаписываться при повторном сканировании | 2026-07-31, `590eded` | Для комментариев, впервые увиденных после этого коммита, `fetched_at` — время первого захвата и годится для отбора периода. |
| В БД добавлены `reply_batches`, `comment_batch_queue`, `reply_batch_items` | 2026-08-28, `1d3682e`, миграция `0008_reply_batches` | С этого момента технически могут появляться batch-записи; сама таблица не доказывает, что режим был включён. |
| Batch-логика подключена к циклу | 2026-08-28, `2335aeb` | При включённом runtime-флаге комментарии с `post_url` могут генерироваться пакетами. |
| Появилась отдельная очередь публикации | 2026-09-10, `859c0ed` и `99c2dd9`, миграция `0009_article_publication_queue` | Для ответов, созданных после этого релиза, есть данные о попытках публикации и их последнем результате. Для июля такого журнала нет. |

Фактическая дата включения batch-режима не хранится в git: runtime-конфиг
перезаписывается hot reload-ом и не имеет истории аудита
([`runtime_config.py`](../../dzen_commenter/config/runtime_config.py)). Её нельзя
заменять датой коммита или миграции. В production-периоде надёжный индикатор
фактического использования — наличие строк `reply_batches`/`reply_batch_items`;
точную дату включения нужно подтвердить первой такой строкой, настройкой и/или
логом запуска.

## Как теперь записывается жизненный цикл

### Общие сущности

`comments` хранит исходный комментарий, его текст, `posted_at`, первое
`fetched_at`, текущий `status` и `post_url`. `replies` хранит каждую созданную
попытку ответа: текст, provider/model, `created_at`, финальный статус,
`published_at` и `error_reason`. Схема: [`models.py`](../../dzen_commenter/db/models.py).

Статусы комментария: `new`, `answered`, `skipped`, `error`; статусы ответа:
`generated`, `published`, `error`, `skipped`
([`enums.py`](../../dzen_commenter/contracts/enums.py)).

Важно: `comments.status` — **не исторический журнал**. `upsert_comment` при
повторном сканировании записывает входящий статус комментария снова
([`repository.py`](../../dzen_commenter/db/repository.py)). Поэтому нынешнее
значение `comments.status` нельзя без дополнительной проверки трактовать как
исход конкретного старого комментария.

### Одиночный путь до batch

На конце июля цикл последовательно брал видимый комментарий, вызывал LLM,
сохранял один `replies`-ряд и сразу пытался опубликовать его
(`git show 8bc9cb4:dzen_commenter/orchestrator/loop.py`). Пустой
ответ переводил только комментарий в `skipped`; отдельная строка `replies` при
этом не создавалась. Ошибка публикации сразу переводила уже сохранённый ответ в
`error` и также переводила комментарий в `error`.

Следствия для сравнения с июлем:

* число строк `replies` не равно числу просмотренных комментариев: предгенерационные
  пропуски не имеют собственной строки ответа;
* необработанная ошибка LLM до `save_reply` также не получает DB-записи;
* самостоятельной очереди и счётчика попыток публикации в июле не было.

### Batch-генерация

При включённых `batch_replies_enabled` и timezone-aware `batch_cutover_at`
([`runtime_config.py`](../../dzen_commenter/config/runtime_config.py)) комментарий
с `post_url` попадает в `comment_batch_queue`. Claim выбирает комментарии только
одного `post_url`; неполный набор ждёт `batch_wait_hours`, полный ограничивается
`batch_max_comments` и остатком часовой квоты
([`repository.py`](../../dzen_commenter/db/repository.py), `claim_next_batch`).

Для каждого claim создаются:

* `reply_batches`: время `created_at`, число элементов, итог batch и одна
  `error_reason`;
* `reply_batch_items`: связь «batch—комментарий», исходный номер и ссылка на
  созданный `replies`-ряд;
* `comment_batch_queue`: счётчик batch-попыток, состояние и время следующей
  попытки.

При `REPLY` создаётся `replies.status = generated`, при `SKIP` —
`skipped`, при `ERROR` — `error`; для `REPLY` в той же транзакции создаётся
задание на публикацию. Ошибочный batch-элемент повторяется до
`batch_max_attempts_per_comment`
([`repository.py`](../../dzen_commenter/db/repository.py), `save_batch_outcomes`).

Строгий multi-item parser требует ровно столько строк, сколько было элементов,
и соответствующие порядковые метки. Если такой parser падает на наборе из более
одного элемента, код делает отдельные single-item LLM-вызовы для каждого элемента
([`loop.py`](../../dzen_commenter/orchestrator/loop.py), `_generate_batch` и
`_generate_single_item_batch_outcomes`; [`batch.py`](../../dzen_commenter/prompt/batch.py)).

Это означает, что реальное число LLM-вызовов и токенов нельзя восстановить из
количества batch-строк: восстановившийся parser failure может оставить только
успешные item-строки. В текущем вызове `save_batch_outcomes` токены передаются
как `None`, поэтому `reply_batches.prompt_tokens` и `completion_tokens` не дают
измерить расход токенов ([`loop.py`](../../dzen_commenter/orchestrator/loop.py)).

### Публикация после 2026-09-10

`reply_publication_queue` содержит одну строку на сгенерированный ответ:
`state`, `attempt_count`, `next_attempt_at`, `last_error`, `created_at`,
`claimed_at` ([`models.py`](../../dzen_commenter/db/models.py)). Ошибка
публикации сначала возвращает job в `queued`; только при исчерпании
`publication_max_attempts_per_reply` ответ становится `error`. Успешный
автопост переводит ответ в `published`; в режиме черновика успешная операция
оставляет его `generated`, но queue становится `completed`
([`repository.py`](../../dzen_commenter/db/repository.py),
`complete_publication` и `fail_publication`).

С 2026-09-15 queued job, у которого `comments.fetched_at` старше
`max_comment_age_days`, намеренно завершает очередь и переводит comment/reply в
`skipped` до попытки браузером (`adac160`, `cd32464`). Такие пропуски нужно
выделять отдельной категорией, а не относить к решению модели или качеству
batch-ответа.

## Метрики, которые можно посчитать из БД

Окна должны иметь одинаковую календарную длину и одинаковые правила границ,
например `[start, end)`. Для «до batch» разумный кандидат — конец июля после
`590eded`; для «после» — окно, полностью после **подтверждённого** первого
batch. Нельзя называть интервал «batch» лишь потому, что он после 2026-08-28.

| Вопрос | Корректная единица / источник | Ограничение интерпретации |
|---|---|---|
| Сколько комментариев было впервые захвачено | Уникальные `comments.id` по `fetched_at` | Это захват, а не обязательно подходящий для ответа комментарий. |
| Сколько batch-элементов сгенерировано | Уникальные `reply_batch_items.comment_id`, связанные с batch в окне | Один комментарий может иметь несколько batch-попыток; для rate нужен уникальный comment, не число item-строк. |
| Результат batch-генерации | Последний по времени `replies`-ряд для comment, связанный с `reply_batch_items`; отдельно `generated/published`, `skipped`, `error` | Статус `error` объединяет ошибку генерации и terminal publication failure; их надо разносить по `error_reason` и publication queue. |
| Явный model `SKIP` в batch | `replies.status = 'skipped'` с join на `reply_batch_items` | Не включает пропуски до создания ответа; не сопоставим один-в-один с июльским `comments.status='skipped'`. |
| Terminal публикационные отказы | Для периода после 2026-09-10: `reply_publication_queue.state='completed'`, `last_error IS NOT NULL`, плюс `replies.status='error'` | В июле не было счётчика повторов; июльский `replies.status='error'` отражал немедленную ошибку. Сравнение — только как разные операционные определения. |
| Повторы публикации | `reply_publication_queue.attempt_count > 1` | Доступно только после миграции `0009`; не сравнивать численно с июлем. |
| Задержка до генерации | batch: `reply_batches.created_at - comments.fetched_at`; одиночный: `replies.created_at - comments.fetched_at` | `fetched_at` — захват ботом, а не время написания пользователем; batch может законно ждать заполнения. |
| Задержка до успешной публикации | `published_at - replies.created_at` только при `auto_publish=true` | При черновиках нет отдельного времени успеха, а `published_at` остаётся NULL. |
| Качество текста | Воспроизводимая ручная выборка финальных непустых `replies.generated_text`, по одному последнему ответу на comment | В DB нет автоматической метки качества, исходного raw-response, prompt или оценки пользователя. |
| Расход LLM и доля parser fallback | Не измеряется ретроспективно текущей схемой | Вызовы и токены не сохраняются, parser failure может быть успешно скрыт fallback-ом. |

## Что нельзя заявлять по одной этой БД

1. **Полный процент пропусков в июле.** У одиночного пути часть пропусков не
   создаёт `replies`, а итог `comments.status` изменяем при последующем scrape.
   Можно дать лишь явно оговорённые прокси-метрики или использовать логи/снимок
   БД того периода.
2. **Число LLM-вызовов, токенов и частоту malformed batch.** Эти события не
   журналируются в сохранённом виде; количество `reply_batches` не равно
   количеству вызовов из-за fallback.
3. **Сопоставимый rate ошибок публикации до и после.** До 2026-09-10 ошибка
   была финальной после первой попытки, после — лишь после retry policy. Для
   честного отчёта надо показывать оба определения и не делать вывод только из
   падения/роста terminal error rate.
4. **Качество модели только по статусам.** `generated/published` означает, что
   текст прошёл технический путь, а не что он уместен, фактически точен или
   хорошо отвечает на комментарий.

## Рекомендуемый протокол итогового отчёта

1. Зафиксировать две одинаковые даты-границы и в отчёте вывести их в ISO-8601 с
   timezone. Сначала доказать, что свежая выборка реально batch: число
   `reply_batches` и `reply_batch_items` в её окне больше нуля.
2. Считать denominators на уровне уникального комментария. Для batch отдельно
   показать число batch-элементов/попыток: это предотвращает маскировку retry
   как новых входящих комментариев.
3. Разнести исходы минимум на: отсутствует reply-ряд, `skipped` с reply-рядом,
   generation error, terminal publication error, успешная queue операция,
   pending/claimed job. Не объединять их в один «пропуск».
4. Для качества сделать одинаковую воспроизводимую выборку из непустых
   финальных текстов обоих окон (например, по 30 уникальных комментариев,
   случайный порядок с зафиксированным seed). Оценивать вручную по заранее
   опубликованной шкале: релевантность комментарию, фактическая осторожность,
   тон, отсутствие шаблонности/сбоя формата. Хранить ID и оценку каждого текста
   в приложении к отчёту, чтобы средние не были неподтверждёнными.
5. Любую разницу формулировать как наблюдение для выбранных когорт, а не как
   причинный эффект batch: одновременно менялись prompt, article context,
   retry-логика и поведение публикации.
