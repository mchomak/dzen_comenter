## Техническое содержание ключевых вех

### `5eab5ff` — наиболее точный pre-batch кандидат

Это именно ревизия «очистка статей уже есть, batch ещё нет». Её родитель: `6a2bb885a798064f0ae555e34635663b793762b8`.

В `dzen_commenter/dzen/page.py` коммит ждёт `[class*="article-render__container"]`, берёт `h1` и только дочерние `p`, `h2`–`h4`, `li`, `blockquote`; `figcaption` исключаются. Также отбрасываются блоки с ограниченным набором маркеров, в том числе `domeo`, `калькулятор`, `подписывайтесь`, `читайте ещё`, `бесплатно рассчита`. Поэтому это не доказательство удаления *всей* рекламы: фильтр маркерный, а при неуспешном извлечении остаётся fallback к `article.inner_text()`.

Именно от этой ревизии до первого коммита batch-storage `1d3682ef897d52fa76d6b59c07b8599fea119ccc` прошло 3 дн. 15 ч. 53 мин. 25 с.; до переключения цикла `2335aeb` — 3 дн. 16 ч. 13 мин. 51 с.

### 28–30 августа — не один change, а серия несовместимых ранних протоколов

`1d3682e` добавил storage и runtime-настройки, `e066e34` потребовал cutover timestamp, `6ee6a64` ввёл batch prompt и строгий parser, `2335aeb` подключил их к циклу. Само наличие этих коммитов не доказывает, что batch был включён: это определяется изменяемыми `batch_replies_enabled` и `batch_cutover_at` в runtime JSON.

С 30 августа 15:43:52 до 20:49:25 последовали как минимум девять относящихся к протоколу коммитов: `2bb84aa`, `8251e93`, `dae0585`, `c51af57`, `d6fee18`, `6d0bf96`, `df39cf0`, `5b157bb`, `9e3b38a`. Среди них:

- `2bb84aa` исправляет сохранение и парсинг строк batch;
- `d6fee18` при `BatchParseError` multi-item batch переходит к отдельным one-item генерациям;
- `5b157bb` и `9e3b38a` вводят/расширяют свободный формат для batch размера 1.

Следствие для статистики: период до 30 августа нельзя считать единой зрелой batch-версией, а число AI-вызовов нельзя выводить только из количества созданных batch: malformed multi-batch может разложиться на одиночные генерации.

### Источник вероятного дефекта промпта, не связанный с размером 3

До `8dc494c` batch builder уже требовал общий транспортный формат `Cnn | текст` либо `Cnn | SKIP`. Но в каждую карточку после этого протокола подставлялся `config.task_lead` или `config.task_engage`. Версия `prompt_config.example.json` на ревизии `6ee6a64` требовала от каждого задания два поля: `тип: <...>` и `ответ: <...>`; дефолтные anti-rules тоже предписывали `тип: пропуск`.

Это внутреннее противоречие исходного промпта: формат всего batch запрещает служебные поля, а более поздняя инструкция внутри карточки требует их. Оно делает утечку `тип:`/`ответ:` правдоподобной без предположения, что модель не справляется именно с тремя комментариями. Это исходный причинный механизм, а не доказательство того, какие именно runtime-поля были на production.

`8dc494c` устраняет обе стороны: дефолты говорят возвращать только `SKIP`, задачи не содержат «Тип:», финальное правило размещается после карточек, а `sanitize_model_reply` удаляет служебные префиксы и превращает `пропуск`/`SKIP` в skip outcome.

### 5–15 сентября — изменился и сам смысл «пропуска»/«ошибки публикации»

- `25b0d11` отменил кратковременное требование брать batch только из текущего DOM. Комментарий мог быть сгенерирован, хотя его нельзя было немедленно найти для публикации.
- `15e6994` (2026-09-07 15:44:23) изменил outcome отсутствующего DOM-комментария с `ERROR` на `SKIP`.
- `859c0ed`/`99c2dd9` добавили durable publication queue и повторную публикацию. С этого момента одна генерация может иметь несколько DOM-попыток публикации и terminal `ERROR` лишь после лимита попыток.
- `4e0d3d2` (2026-09-10 17:05:23) временно требовал видимость комментария для claim publication; `9abb041` (2026-09-14 22:51:43) снял этот фильтр.
- `c9c946c` (2026-09-14 23:11:21) добавил поиск комментария прокруткой до 20 экранов; `adac160` и `cd32464` завершили защиту от устаревших jobs, переводя их в `SKIPPED`.

Поэтому простой ряд `comments.status = skipped/error` до и после сентября — не одинаковая метрика: разные commits записывают в эти статусы возраст, отсутствие DOM, ошибки генерации и terminal publication failure.

## Что измерять на production между границами

Для количественного отчёта интервалы должны строиться по фактическому времени создания данных, а не по одному времени commit. Практичные непересекающиеся технико-логические интервалы:

1. **`5eab5ff` → `2335aeb`**: очищенный контекст и одиночный цикл — целевой кандидат для сравнения с batch.
2. **`2335aeb` → `9e3b38a`**: ранний batch-протокол; анализировать отдельно, не смешивать со зрелым batch.
3. **`9e3b38a` → `25b0d11`**: стабилизированный parser, но публикация ещё в том же цикле и зависит от текущего DOM.
4. **`25b0d11` → `99c2dd9`**: восстановление DB-очереди и новые skip semantics, но до durable publication queue.
5. **`99c2dd9` → `8dc494c`**: durable publication queue при ещё противоречивом source prompt.
6. **после `8dc494c`**: metadata sanitation присутствует; после 15 сентября дополнительно меняются поиск/срок годности публикации.

Для датированных комментариев `comments.fetched_at` становится временем первого обнаружения только после `590eded`. До фактического deployment этого коммита окно по `fetched_at` может включать старый комментарий, увиденный повторно; для раннего июля это ограничение обязательно указывать. Ответы лучше группировать по `replies.created_at`, а публикационные проблемы — отдельно по очереди и terminal reply status.

## Причинные ограничения

1. Git timestamp — время коммита, не время deployment, migration или смены runtime JSON. Git не доказывает, что процесс на сервере был перезапущен именно в этот момент.
2. Runtime prompt и batch flags hot-reloadятся. Source defaults/example показывают допустимое поведение кода, но не подтверждают production custom text.
3. Несколько изменений часто попали в период меньше суток; без данных по фактической версии контейнера нельзя приписывать смену метрики одному hash.
4. Ошибки сервиса/сети/Дзена и сезонное изменение входящего потока являются смешивающими факторами; их надо разложить по `error_reason`, а не считать общим числом `ERROR`.
5. Стабильность определяется наблюдаемой статистикой в DB/logs. Git позволяет выделить сравнимые версии и исключить некорректные сравнения, но сам не выбирает «максимально стабильное» состояние.
