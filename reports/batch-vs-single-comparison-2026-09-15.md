# Batch-генерация vs одиночный режим — сравнение production-данных

Дата исследования: 2026-09-15. Доступ к production — только чтение. Исходные комментарии, ответы и идентификаторы в отчёт не включены.

## Короткий вывод

1. Фактический post-batch режим в выбранном окне почти не генерировал ответы «по три»: 619 из 726 batch (85,26%) содержали один комментарий, 80 (11,02%) — два и 27 (3,72%) — три. Тройные batch дали 81 из 860 обработанных элементов (9,42%).
2. Семь зафиксированных generation-error post-batch периода пришлись на batch размера 1: пять `read operation timed out` и два `Batch line count does not match claimed items`. Данных, что именно генерация трёх ответов вызвала эти ошибки, нет.
3. Качество сохранённого текста в post-batch периоде имеет объективный дефект формата: служебный префикс `тип: … ответ:` есть у 247 из 359 опубликованных ответов (68,80%), а последовательность вида `тип: … SKIP` — у 52 из 359 (14,48%). В июльском окне обе величины равны 0 из 1 048 непустых сохранённых ответов.
4. Ручная оценка 12 случайных пар «комментарий + ответ» дала 5,83/8 в июле и 3,92/8 post-batch; отдельная выборка 12 ответов из тройных batch — 4,08/8. Это малый неслепой экспертный sample, а не статистическое доказательство, но он согласуется с объективным дефектом формата.
5. Post-batch ошибок в БД записано больше: 90 reply-error против 1 в июле. Их нельзя честно трактовать как рост частоты, потому что durable publication queue появилась только 10 сентября, а старый путь иначе сохранял пропуски и ошибки.
6. По доступным данным польза именно от объединения трёх комментариев не подтверждена: тройные batch редки, а batch-формат связан с существенным риском публикации служебного текста. Экономию AI-вызовов сравнить нельзя — исторических счётчиков одиночных запросов/токенов за июль нет.

## Данные и дизайн сравнения

### Окна

| Период | Границы в БД | Длина | Режим |
| --- | --- | ---: | --- |
| До batch | 2026-07-25 00:00:00 ≤ `fetched_at` < 2026-08-01 00:00:00 UTC | 7 полных дней | до первых `reply_batches` |
| После batch | 2026-09-08 00:00:00 ≤ `fetched_at` < 2026-09-15 00:00:00 UTC | 7 полных дней | после первого `reply_batches` (2026-08-30) |

PostgreSQL сообщил `TimeZone = Etc/UTC`. Текущий день 15 сентября исключён. Объём входящих комментариев почти одинаков: 1 123 до batch и 1 132 после него.

### Первичные источники

- Read-only PostgreSQL: `comments`, `replies`, `reply_batches`, `reply_batch_items`, `reply_publication_queue`.
- Исходный код и история: [модель данных и ограничения сравнения](../docs/research/batch-comparison-data-model.md), `dzen_commenter/prompt/batch.py`, `dzen_commenter/db/repository.py`.
- Точные read-only запросы агрегатов и детерминированной выборки: [batch-comparison-sql.md](../docs/research/batch-comparison-sql.md).

Первый `reply_batches.created_at` — 2026-08-30 15:47:07 UTC. Первые `reply_publication_queue.created_at` — 2026-09-10 11:09:08 UTC. Поэтому queue-метрики отсутствуют для июля по архитектурной причине.

## Статусы и ошибки: сырые числа

| Показатель по комментариям, собранным в окне | До batch | После batch |
| --- | ---: | ---: |
| Комментарии | 1 123 | 1 132 |
| Текущий `comments.status = skipped` | 1 005 (89,49%) | 463 (40,90%) |
| Текущий `comments.status = error` | 0 (0,00%) | 58 (5,12%) |
| Связанные записи `replies` | 1 048 (93,32% от comments) | 822 (72,61%) |
| `replies.status = published` | 13 | 359 |
| `replies.status = generated` | 1 034 | 117 |
| `replies.status = skipped` | 0 | 256 |
| `replies.status = error` | 1 | 90 |

Эта таблица — факт о текущем состоянии строк, но не корректная таблица «изменения эффективности»:

- `comments.status` — не исторический журнал; upsert может менять статус при повторном сканировании.
- Июльский путь не создавал `replies` для части пропусков; post-batch путь создаёт `ReplyStatus.SKIPPED`.
- Durable publication queue, три попытки публикации и terminal publication errors отсутствовали в июльской архитектуре.

Следовательно, разность 90 против 1 показывает рост **наблюдаемых и записанных** ошибок, но не измеряет причинный рост ошибок модели из-за batch.

### Разбор 90 post-batch reply-error

| Класс ошибки | Число | Доля от 822 `replies` |
| --- | ---: | ---: |
| Batch generation error | 7 | 0,85% |
| Terminal publication error: комментарий не найден в DOM | 83 | 10,10% |
| Всего | 90 | 10,95% |

Все 7 generation-error относятся к batch из одного элемента: 5 таймаутов чтения и 2 ошибки несовпадения числа строк. Это отделяет наблюдаемую `BatchParseError` от гипотезы о неспособности модели сформировать три ответа сразу.

## Что фактически происходило в batch

| Размер batch | Batch-вызовы | Доля batch-вызовов | Элементы |
| ---: | ---: | ---: | ---: |
| 1 | 619 | 85,26% | 619 |
| 2 | 80 | 11,02% | 160 |
| 3 | 27 | 3,72% | 81 |
| Всего | 726 | 100,00% | 860 |

Из 860 элементов: 580 получили outcome `generated`, 273 — `skipped`, 7 — `error`. Средний размер batch — 1,18, медиана — 1. Следовательно, основная нагрузка в этом окне шла через одноэлементный batch-протокол, а не через ожидаемую группировку по три.

## Дефект формата в сохраняемых и опубликованных текстах

Batch prompt требует «только готовый текст» и прямо запрещает метки `тип:` / `ответ:`. Для batch из 1 `parse_batch` допускает произвольную одну строку как ответ; поэтому модельный служебный шаблон не отвергается автоматически.

| Наблюдение | До batch | После batch |
| --- | ---: | ---: |
| Непустые `generated_text` | 1 048 | 559 |
| Содержат `тип: … ответ:` | 0 | 413 (73,88% от непустых) |
| Содержат `тип: … SKIP` | 0 | 131 (23,43% от непустых) |
| Опубликованные ответы | 13 | 359 |
| Опубликованные с `тип: … ответ:` | 0 | 247 (68,80% от published) |
| Опубликованные с `тип: … SKIP` | 0 | 52 (14,48% от published) |

По размерам batch доля опубликованных с префиксом `тип: … ответ:` составила: 208/267 для размера 1, 26/63 для размера 2 и 13/26 для размера 3. В тройных batch это 50,00% опубликованных ответов. Дефект не ограничен batch размера 1.

Это сильнее, чем впечатление от отдельных сообщений: служебные метки и `SKIP` присутствуют в сохранённых строках и дошли до статуса `published`. Однако источник данных не позволяет утверждать, что именно batch как таковой — единственная причина: одновременно могли меняться prompt или runtime-конфигурация.

## Ручная оценка качества

### Метод

Использован seed `quality-v1`: в каждом наборе 12 строк выбраны сортировкой `md5(reply_id || 'quality-v1')`. Оценивалась сохранённая пара «комментарий + ответ» по четырём шкалам 0–2: релевантность, отсутствие видимой выдумки в доступном контексте, тон/язык, полезность. Максимум — 8.

`0` означает явный провал критерия, `1` — частичное выполнение, `2` — выполнение. Оценка не проверяет внешние факты и не заменяет редакторскую экспертизу. Периоды при чтении не были скрыты, поэтому возможен confirmation bias; это ограничение нельзя ретроспективно устранить.

| Выборка | n | Среднее / 8 | Медиана / 8 | Сумма баллов | Ответы с total ≤ 1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| До batch, случайная | 12 | 5,83 | 6,0 | 70 | 0 |
| После batch, случайная | 12 | 3,92 | 5,5 | 47 | 4 |
| После batch, только batch размера 3 | 12 | 4,08 | 4,5 | 49 | 3 |

Для проверки арифметики сохранены обезличенные последовательности итоговых баллов в порядке детерминированной сортировки (без текстов и идентификаторов). Каждый итог — сумма четырёх оценок: релевантность, обоснованность, тон/язык и полезность.

| Выборка | Векторы оценок по rank 1…12 | Сумма total |
| --- | --- | ---: |
| До batch | `7, 7, 5, 5, 6, 8, 5, 3, 4, 7, 6, 7` | 70 |
| После batch | `6, 7, 4, 6, 1, 0, 0, 6, 6, 5, 6, 0` | 47 |
| Batch размера 3 | `3, 4, 6, 6, 4, 0, 6, 7, 0, 1, 7, 5` | 49 |

Это воспроизводит отбор и расчёт агрегатов, но не делает экспертную оценку «слепо проверяемой»: исходные тексты намеренно не публикуются. Поэтому качественный вывод остаётся малым неслепым sample, а не независимой статистической экспертизой.

В post-batch sample повторялись три наблюдаемых типа дефекта: служебные префиксы, переданный как текст `SKIP`/`пропуск`, и нерелевантный ответ с уходом в другую тему. В pre-batch sample встречались общие и мало полезные ответы, но не было служебных меток. Из-за `n = 12` разность баллов — сигнал для исправления и повторной проверки, а не оценка точного популяционного эффекта.

## Паттерны и ограничения

1. Размер batch и generation error: все 7 ошибок пришлись на размер 1; для размера 2 и 3 в окне generation-error не записаны. Малое число ошибок не позволяет строить надёжную статистическую связь, но гипотеза «ошибки вызваны именно тремя ответами» не подтверждается.
2. Размер batch и дефект меток: published-префиксы есть при размерах 1, 2 и 3; проблема шире одного fallback-пути.
3. Ошибки публикации (83) — отдельный DOM-процесс, не оценка качества LLM. Они связаны с тем, что комментарий не найден при публикации, и не должны смешиваться с 7 generation-error.
4. Метрика задержки `replies.created_at - comments.fetched_at` непригодна: для июля среднее −555,5 минуты, медиана −401,5 минуты. Это прямой признак перезаписи `fetched_at` при upsert, а не «ответа до комментария».
5. AI provider/model в обоих окнах одинаковы для связанных replies: `gigachat` / `GigaChat-Pro`. Историю prompt и runtime-настроек БД не хранит, поэтому их изменение остаётся неконтролируемым confounder.

## Итоговая оценка «польза или вред»

Для вопроса о тройной генерации: данных о пользе недостаточно — тройные batch составили только 3,72% batch-вызовов. Для качества и безопасности публикации в данном окне наблюдается вред: служебный формат попал в 68,80% опубликованных post-batch ответов, а ручный sample ниже июльского на 1,91 балла из 8. Для надёжности сравнение «до/после» невалидно без учёта изменившегося хранения ошибок, но внутри post-batch периода генерационные ошибки составили 7/860 элементов и не связаны с размером 3.

Нужна отдельная проверка после исправления парсинга/форматного контроля: те же 7-дневные показатели, доля служебных токенов в published и новый слепой sample. Только так можно измерить эффект исправления, не смешивая его с изменениями схемы и публикационной очереди.

## Воспроизводимость агрегатов

Периоды выбирались `comments.fetched_at`; `replies` присоединялись по `replies.comment_id = comments.id`. Batch distribution считался по `reply_batches.created_at` и `reply_batch_items`. Маркеры формата определялись наличием слов `тип:` и `ответ:` либо `тип:` и `SKIP`, без требования их непосредственного соседства. Полные исполнимые read-only SQL-выражения приведены в [batch-comparison-sql.md](../docs/research/batch-comparison-sql.md); сырые строки намеренно не сохраняются в репозитории.
